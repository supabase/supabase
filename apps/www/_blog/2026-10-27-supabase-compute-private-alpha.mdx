Today we're launching Supabase Compute in private alpha. It runs your agents inside your Supabase project, next to their data and memory. Background jobs and APIs run there too. It's for teams whose data is on Supabase but whose agents run somewhere else. Compute is free during the alpha and runs in us-west-2. [Join the waitlist](https://supabase.com/compute#waitlist) to try it.

Developers told us some work doesn't fit in an Edge Function. Some work needs more memory or CPU. Some runs longer than 400 seconds, like an AI agent. Some is written in another language.

That work usually means a second platform, with its own deploys, its own logs, and debugging across two providers. Supabase Compute brings that work into your project. You pick the size, the work runs for minutes or hours, and you deploy Node, Deno, or any Dockerfile.

## What you can run

Each service gets a full Linux environment, so you can run:

- An agent that works through a task for minutes
- A background job that pulls work from a Postgres queue
- A data sync or embedding backfill that runs for hours
- An API in another language, from a Dockerfile
- A voice agent that holds a WebSocket open for a session, with your client reconnecting if the instance is replaced
- A small open-source model in Python, running on CPU

## Deploy with the Supabase CLI

Compute uses the Supabase CLI you already have, v2.120.0 or later. Once you have access:

1. Add `compute = true` under `[experimental]` in `supabase/config.toml`.
2. Create a service with `supabase compute new`. Pick a runtime (Node, Deno, or a Dockerfile), a size (2 GB with 1 vCPU, or 4 GB with 2 vCPUs), and whether the service is public, with a URL, or private, with no URL.
3. Replace the starter code in the service's folder, under `supabase/compute/`, with your own.
4. Deploy it with `supabase compute push`.

A service's settings are a few lines in `config.toml`, so your coding agent can write them and deploy the service for you. Point your agent at the Compute guide. The Management API also has alpha endpoints to deploy, list, and delete services.

Your services get your project's secrets. Their logs show up on the Compute page in your dashboard.

## Keep your agent's memory in Postgres

A service can run with no time limit. But instances can be replaced at any time, so save your agent's progress to Postgres. Your code can then pick up where the last instance stopped.

Your agent's memory can live in Postgres too, with pgvector for search. Supabase Compute runs in us-west-2, the same region as your database, so queries stay fast. Dreambase [quickly moved their data agent onto Compute](https://dreambase.com/blog/running-our-data-pipeline-on-supabase-compute) to test it. Queries to Postgres took a median of 2.9 ms, versus 65 ms from another region.

## What to know about the private alpha

- It's for evaluation, not production, and it may change or end.
- Only projects in us-west-2 can use it.
- Every service gets all of your project's secrets.
- There's no autoscaling, GPU, or persistent disk.
- Public services suspend when idle. Private services keep running.
