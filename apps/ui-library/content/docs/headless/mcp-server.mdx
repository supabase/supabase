Give external agents such as Codex, Claude Code, and ChatGPT secure, user-scoped
access to your product through composable MCP tools. This block runs as a
Supabase Edge Function and pairs with the
[OAuth Consent block](../nextjs/oauth-consent) to authorize signed-in users.

## Configure the project

The function verifies OAuth tokens, so disable the gateway JWT check:

```toml
[functions.mcp-server]
verify_jwt = false
```

Install the [OAuth Consent block](../nextjs/oauth-consent), then enable OAuth and
dynamic client registration:

```toml
[auth.oauth_server]
enabled = true
authorization_url_path = "/oauth/consent"
allow_dynamic_registration = true
```

Set the Auth **Site URL** to the origin that hosts `/oauth/consent`. Use HTTPS in
production. Run `supabase config push` or restart the local stack after changing
`supabase/config.toml`.

Dynamic registration lets any compatible client register. Review clients and
let users revoke grants, or disable it if you register clients manually.

Use an ES256 or RS256 signing key when clients request `openid`; HS256 cannot
issue ID tokens. Configure keys in the
[JWT Signing Keys dashboard](https://supabase.com/dashboard/project/_/settings/jwt).
Rotation affects all new project tokens, so check other token consumers first.

## Authentication

`withOAuthProtectedResource` serves RFC 9728 metadata at
`/functions/v1/mcp-server/oauth-protected-resource` and adds a
`WWW-Authenticate` challenge to `401` responses so MCP clients can discover the
authorization server.

`withSupabase({ auth: 'user' })` verifies the JWT and provides an RLS-scoped
client. The handler also requires `client_id`, so ordinary user JWTs are
rejected and only OAuth access tokens can call tools. Each tool inherits that
user-scoped client.

OAuth scopes control identity, not data or tools. Enforce every operation with
Row Level Security (RLS). Use `client_id` for client-specific policies, and do
not expose sensitive admin tools.

## Add tools

`tools/index.ts` is the only registry. Add each toolset to its array:

```ts
// supabase/functions/mcp-server/tools/tasks.ts
import { z } from 'npm:zod@4.4.3'

import { jsonResult, runtimeErrorResult } from './result.ts'
import type { Toolset } from './types.ts'

export const tasksToolset: Toolset = {
  name: 'tasks',
  register(server, { supabase }) {
    server.registerTool(
      'close_task',
      {
        description: 'Mark a task as closed.',
        inputSchema: { id: z.string().uuid() },
        annotations: { readOnlyHint: false, idempotentHint: true },
      },
      async ({ id }) => {
        try {
          const { data, error } = await supabase
            .from('tasks')
            .update({ closed: true })
            .eq('id', id)
            .select()
          if (error) throw error
          return jsonResult(data)
        } catch (error) {
          return runtimeErrorResult(error)
        }
      }
    )
  },
}
```

```ts
import { tasksToolset } from './tasks.ts'
import { whoamiToolset } from './whoami.ts'

const toolRegistry: readonly Toolset[] = [whoamiToolset, tasksToolset]
```

Each toolset receives:

- `supabase`, a user-scoped client for Database, Auth, Storage, and Functions
- `fetchSupabase(path, init)` calls project APIs without exposing the token
- `claims` and `clientId` for the verified identity

`register` can be async, so future schema-based toolsets can inspect project APIs
without changing the server core. Duplicate toolset names fail at startup.

## Environment

| Variable                 | Default          | Purpose                          |
| ------------------------ | ---------------- | -------------------------------- |
| `MCP_SERVER_NAME`        | `supabase-mcp`   | Server name shown to MCP clients |
| `MCP_SERVER_DESCRIPTION` | Generic sentence | Instructions shown to clients    |

```bash
supabase config push
```
