The same user-scoped MCP server as the [MCP Server](./mcp-server) block, running
as a Supabase Compute service instead of an Edge Function. Same libraries, same
pipeline, same tools: `@supabase/middleware` for composition, `@supabase/server`
for the auth gate and OAuth discovery, and an RLS-scoped client for every tool.

Reach for this when the server needs more memory or a longer request than Edge
Functions gives it. Reach for the Edge Function block otherwise: it needs no URL
configuration.

## Installation

<BlockItem name="mcp-server-compute" showOpenInV0={false} />

Installs Deno Compute files into a Supabase project or empty directory. No
`components.json` is required. Backend files stay in `supabase/` at the project
root even when the frontend uses `src/`.

The tool files are the same files the Edge Function block installs, written to
`supabase/compute/mcp-server/tools/`. A tool written once works on both runtimes.

## Configure the project

Compute is experimental, so opt in and declare the service in
`supabase/config.toml`:

```toml
[experimental]
compute = true

[compute.mcp-server]
runtime = "deno"
size = "2gb"
exposure = "public"
```

`runtime = "deno"` serves `main.ts`'s default-exported `fetch` handler with no
build step, and resolves the `npm:` and `jsr:` specifiers at startup, so nothing
is vendored into the repo. It is also what lets this block share the Edge
Function block's tool files unchanged: those files import through `npm:`
specifiers and explicit `.ts` paths. `exposure = "public"` publishes the service at
`https://<project-ref>.supabase.co/compute/v1/mcp-server`. The name in
`[compute.<name>]` is the last segment of that URL.

The project must sign JWTs with an asymmetric key. `withSupabase` verifies user
tokens against the project JWKS and rejects legacy HS256 tokens, so a project
that still uses the legacy secret cannot authenticate embedded product sessions
or external MCP clients. Switch to an ES256 or RS256 key in
[JWT Keys](https://supabase.com/dashboard/project/_/settings/jwt).

Use `supabase@beta`, since `supabase compute` is still behind the beta channel.

## Choose how agents authenticate

Both methods work exactly as they do on Edge Functions. `withSupabase({ auth: 'user' })`
accepts both token shapes, and the `whoami` tool reports which one a caller used.

### Embedded product agents

A trusted product backend can forward its signed-in user's Supabase access
token as `Authorization: Bearer <token>`. This reuses the product session, so
the user does not need to authorize their own product again.

Keep the token inside your backend or agent orchestrator. Never place it in a
prompt or expose it directly to a model provider.

### External MCP clients

External clients authenticate with OAuth, so users approve and revoke each
client separately. Install the [OAuth Consent block](../nextjs/oauth-consent),
then enable OAuth in `supabase/config.toml`:

```toml
[auth.oauth_server]
enabled = true
authorization_url_path = "/oauth/consent"
allow_dynamic_registration = true
```

Set the Auth **Site URL** to the origin that serves `/oauth/consent`. Use HTTPS
in production. Run `supabase config push` or restart the local stack to apply the
change.

To use a third-party OAuth 2.1 provider as the authorization server instead of
Supabase Auth, set `MCP_AUTHORIZATION_SERVER` to its issuer URL. The rest of the
pipeline is unchanged: the gate still verifies the token against the project's
JWKS, so the provider must be configured as a third-party auth provider on the
project.

## Authentication

The service is a `pipeline` from `@supabase/middleware` with two entries from
`@supabase/server`, in this order:

```ts
const fetchHandler = pipeline(
  [
    withOAuthProtectedResource({ resourceServer, authorizationServer: AUTHORIZATION_SERVER }),
    withSupabase({ auth: 'user', cors: { headers: CORS_HEADERS } }),
  ],
  (request, ctx) => handleMcp(request, ctx)
)

export default { fetch: fetchHandler }
```

`withOAuthProtectedResource()` runs before the auth gate. It serves RFC 9728
metadata at `/compute/v1/mcp-server/oauth-protected-resource` and adds a
`WWW-Authenticate` challenge to `401` responses so MCP clients can discover the
authorization server.

`withSupabase({ auth: 'user' })` is the gate. It verifies the JWT and hands
`handleMcp` an RLS-scoped client. It accepts both product session tokens and
OAuth access tokens. OAuth tokens include `client_id`; ordinary product sessions
do not. The included `whoami` tool exposes that difference.

Any holder of a valid user token can call this service directly. Treat its tools
as an authenticated product API: keep RLS enabled, check authorization for
business operations, and do not add admin clients to the shared tool context.

OAuth scopes control identity, not database or tool access. Use `client_id` for
client-specific policies when it is present, and define the intended behavior
for product sessions where it is null. Never use user-editable metadata for
authorization decisions.

### Why the URLs are passed explicitly

On Edge Functions both advertised URLs are derived from the request. Off Edge
Functions they cannot be: a Compute instance listens on an internal host and
`$PORT`, and its own origin says nothing about the project's public origin.

`@supabase/server` treats any Deno runtime as Edge Functions, so on Compute its
defaults take the Edge Functions path instead of refusing to guess. Left to
them, a request that arrives at the service root fails with
`MISSING_RESOURCE_SERVER`, and one that arrives with its path intact advertises
`https://<project-ref>.supabase.co/functions/v1/compute/v1/<name>`. RFC 9728
§3.3 requires the advertised resource identifier to equal the URL the client
called, so `main.ts` passes both options, resolving them in this order:

1. `MCP_RESOURCE_SERVER`, for a custom domain or a proxy in front of the service.
2. `SUPABASE_PUBLIC_URL`, then `SUPABASE_URL`, joined with
   `/compute/v1/$MCP_COMPUTE_SERVICE_NAME`. This spells the public Compute URL
   exactly, and it does not depend on what a gateway forwards.
3. `X-Forwarded-Proto` and `X-Forwarded-Host` on the request, as a last resort.
4. Otherwise the request fails with a message naming the variables to set.

`authorizationServer` follows the same precedence, with
`MCP_AUTHORIZATION_SERVER` first and `fromSupabaseUrl()` on the project URL
after it. It needs no request, so it resolves at startup: a missing project URL
fails the deploy rather than every request.

## Add tools

Tools are written exactly as in the [MCP Server](./mcp-server) block, in
`supabase/compute/mcp-server/tools/`. Each module exports one registration
function, and `tools/index.ts` is the single composition point.

## Environment

| Variable                   | Default          | Purpose                                            |
| -------------------------- | ---------------- | -------------------------------------------------- |
| `SUPABASE_URL`             | none             | Project URL, required                              |
| `SUPABASE_PUBLISHABLE_KEY` | none             | Publishable key, required                          |
| `MCP_COMPUTE_SERVICE_NAME` | `mcp-server`     | Last segment of the public URL                     |
| `MCP_RESOURCE_SERVER`      | derived          | Override the advertised resource URL               |
| `MCP_AUTHORIZATION_SERVER` | project Auth     | Third-party OAuth 2.1 issuer                       |
| `MCP_SERVER_NAME`          | `supabase-mcp`   | Server name shown to MCP clients                   |
| `MCP_SERVER_DESCRIPTION`   | Generic sentence | Instructions shown to clients                      |

A Compute instance is not given the project URL and API keys automatically, the
way an Edge Function is. Set them yourself. The block includes
`supabase/compute/mcp-server/.env.example`:

```bash
cp supabase/compute/mcp-server/.env.example supabase/compute/mcp-server/.env
```

Add `supabase/compute/mcp-server/.env` to `.gitignore`.

## Deploy

```bash
supabase config push
supabase secrets set --env-file supabase/compute/mcp-server/.env
supabase compute push mcp-server
supabase compute status mcp-server
```

Then check the advertised metadata matches the URL clients call:

```bash
curl https://<project-ref>.supabase.co/compute/v1/mcp-server/oauth-protected-resource
```

`resource` in the response must be
`https://<project-ref>.supabase.co/compute/v1/mcp-server`. If it carries
`/functions/v1`, the environment is missing `SUPABASE_URL`. Use
`supabase compute logs mcp-server` for startup and request errors.
