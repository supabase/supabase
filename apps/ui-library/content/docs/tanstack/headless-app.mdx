Most of this product is used through an agent, not a browser. The app still needs
a place for users to sign in, approve the agents that ask for access, and revoke
them later. This block installs that app: password auth, an OAuth 2.1 consent
screen, an MCP server, and an `/agents` route that manages the connections
between them.

Everything the app serves is either an auth screen or a grant screen, so it runs
on TanStack Start rather than a heavier framework. Supabase holds the state.

## What it installs

| Block                                                             | What it covers                                    |
| ----------------------------------------------------------------- | ------------------------------------------------- |
| [Password-Based Auth](/library/docs/tanstack/password-based-auth) | Sign-in, sign-up, and the `_protected` layout     |
| [OAuth Consent](/library/docs/tanstack/oauth-consent)             | The `/oauth/consent` route agents are sent to     |
| [MCP Server](/library/docs/headless/mcp-server)                   | The Edge Function agents call, scoped to the user |

On top of those, it adds `/agents` and a `supabase/config.toml` with the settings
the three blocks need.

## Configure the project

The block writes `supabase/config.toml`. Installing over an existing file
replaces it, so merge your own settings back in afterwards. The parts that matter
for this app:

```toml
[auth]
site_url = "http://localhost:3000"

[auth.oauth_server]
enabled = true
authorization_url_path = "/oauth/consent"
allow_dynamic_registration = true

[functions.mcp-server]
verify_jwt = false
```

`site_url` must be the origin that serves `/oauth/consent`, since that is where
Auth sends users to approve a client. Use HTTPS in production.
`allow_dynamic_registration` lets any compatible client register itself; set it
to `false` to register clients yourself.

The app reads two environment variables from `.env.local`:

```env
VITE_SUPABASE_URL=
VITE_SUPABASE_PUBLISHABLE_KEY=
```

Find them in the [Connect modal](https://supabase.com/dashboard/project/_?showConnect=true&connectTab=frameworks&framework=react&using=vite&with=supabasejs),
or run `supabase status` against a local stack.

## The agents route

`routes/_protected/agents.tsx` sits under the `_protected` layout route, so
signed-out visitors are redirected to `/login` before it renders and the
signed-in user arrives through the layout's context.

The route reads the user's OAuth grants and renders one of two states. With no
grants, it shows a prompt to paste into an agent. The prompt carries the MCP
server URL, which the route builds from `VITE_SUPABASE_URL`:

```
Connect to Your product using this MCP server:

https://<project-ref>.supabase.co/functions/v1/mcp-server

Then list the tools it gives you.
```

Once a grant exists, the same route lists each authorized client with the scopes
it holds and when the user approved it, and offers **Revoke access**. Revoking
deletes that client's sessions and invalidates its refresh tokens, so the agent
loses access immediately.

Set `PRODUCT_NAME` in `routes/_protected/agents.tsx` to your product's name. It
appears in the prompt and in the page description. The consent screen takes the
same name through the `productName` prop in `routes/oauth/consent.tsx`.

Grants only cover external clients that went through OAuth. An agent that runs
inside your own backend reuses the product session, so it never appears here.

## Run it

Start the stack, serve the function, and run the app:

```bash
supabase start
supabase functions serve mcp-server --env-file supabase/functions/.env
npm run dev
```

The route generator picks up `routes/_protected/agents.tsx` on the next dev
server start and adds it to `routeTree.gen.ts`.

Sign up at `/sign-up`, then open `/agents` and connect an agent with the prompt.
The agent registers itself, sends you to `/oauth/consent`, and appears in the
list once you approve it.

## Deploy

```bash
supabase config push
supabase functions deploy mcp-server
```

Then set the Auth **Site URL** to your deployed origin so consent requests reach
the right app.

This assumes the project signs JWTs with an asymmetric key. A project still using
the legacy HS256 secret cannot issue ID tokens, so clients that request the
`openid` scope fail. Switch to an ES256 or RS256 key in
[JWT Keys](https://supabase.com/dashboard/project/_/settings/jwt).
