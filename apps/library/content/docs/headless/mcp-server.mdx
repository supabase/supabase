An MCP server that runs as one Edge Function. It owns the transport,
authentication, and a registry that toolsets plug into — and nothing else, so the
tools your agents get are the ones you add.

Pair it with [MCP Auth](./mcp-auth) for the browser side of OAuth,
and [MCP Tools: PostgREST](./mcp-tools-postgrest) for database tools
generated from your schema.

## Configure the project

Three pieces of `supabase/config.toml` matter. Add them, then run
`supabase config push` for a linked project or restart the local stack.

```toml
[auth.oauth_server]
enabled = true
authorization_url_path = "/oauth/consent/"
allow_dynamic_registration = true

# Binds OAuth access tokens to this function, using the migration this block
# installs. Without it the server rejects every OAuth token.
[auth.hook.custom_access_token]
enabled = true
uri = "pg-functions://postgres/private/mcp_custom_access_token_hook"

[functions.mcp-server]
# The function verifies bearer tokens itself, as an OAuth protected resource.
verify_jwt = false
```

<Callout type="caution">

The access-token hook is the step most likely to be missed, and it fails
confusingly: registration, consent, and the token exchange all succeed, and only
the first tool call returns 401. The function logs the audience it received and
what to enable when that happens.

</Callout>

## Run it locally

```bash
supabase start
supabase status
cp supabase/functions/mcp-server/.env.example supabase/functions/.env
supabase functions serve mcp-server --env-file supabase/functions/.env
```

Before serving the function, set `MCP_PUBLIC_SUPABASE_URL` in
`supabase/functions/.env` to the **API URL printed by `supabase status`**. Copy
the URL exactly, including its hostname and port. If another local project is
already running, the CLI may assign this project a different port.

The server is then at
`${MCP_PUBLIC_SUPABASE_URL}/functions/v1/mcp-server`. With
`MCP_ALLOW_FIRST_PARTY_JWT=true` you can call it with an ordinary user token,
which is the quickest way to see the tool list. Export the same URL in your
shell before using this example:

```bash
export MCP_PUBLIC_SUPABASE_URL="YOUR_API_URL_FROM_SUPABASE_STATUS"
curl -s "$MCP_PUBLIC_SUPABASE_URL/functions/v1/mcp-server" \
  -H "Authorization: Bearer $USER_ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

## Authentication

The server uses
[`@supabase/server`](https://github.com/supabase/server)'s `verifyAuth` and
`createContextClient` primitives to verify bearer tokens against the project's
JWKS and create a user-scoped Supabase client. It keeps OAuth protected-resource
discovery and audience checks in the block because those are specific to MCP.
Every tool therefore runs under the caller's grants and RLS.

`supabase.ts` resolves the project environment once per worker for internal API
calls and separately resolves the public project URL used by OAuth metadata.
Hosted Edge Functions normally receive the public URL automatically. Locally,
the injected URL may be a Docker-only address such as `http://kong:8000`, so the
server requires `MCP_PUBLIC_SUPABASE_URL` rather than advertising an address
external clients cannot reach. The block uses the standard
`${MCP_PUBLIC_SUPABASE_URL}/functions/v1/mcp-server` endpoint because the
access-token hook mints that exact URL into the token audience.

| Mode                     | Who uses it                                            | What is required                                                     |
| ------------------------ | ------------------------------------------------------ | -------------------------------------------------------------------- |
| OAuth 2.1 client         | External MCP clients: Claude Code, Codex, ChatGPT      | A token carrying `client_id`, audience-bound to this function's URL  |
| First-party Supabase JWT | Your own front-end or agent forwarding a session token | Nothing extra. Set `MCP_ALLOW_FIRST_PARTY_JWT=false` to refuse these |

Both modes revalidate the session against Auth on every request, so revoking a
grant or deleting a session takes effect immediately rather than at token expiry.

## Toolsets

A toolset is a named group of tools that registers itself against the per-request
server. `tools/registry.ts` holds them; `tools/index.ts` lists them.

```ts
// supabase/functions/mcp-server/tools/tasks.ts
import { z } from 'npm:zod@4.4.3'

import type { Toolset } from './registry.ts'
import { jsonResult, runtimeErrorResult } from './result.ts'

export const tasksToolset: Toolset = {
  name: 'tasks',
  description: 'Read and close tasks.',
  register(server, { supabase }) {
    server.registerTool(
      'close_task',
      {
        description: 'Mark a task as closed.',
        inputSchema: { id: z.string().uuid() },
        annotations: { readOnlyHint: false, idempotentHint: true },
      },
      async ({ id }) => {
        try {
          const { data, error } = await supabase
            .from('tasks')
            .update({ closed: true })
            .eq('id', id)
            .select()
          if (error) throw error
          return jsonResult(data)
        } catch (error) {
          return runtimeErrorResult(error)
        }
      }
    )
  },
}
```

Then add it to the manifest:

```ts
// supabase/functions/mcp-server/tools/index.ts
export function registerToolsets(): void {
  registerToolset(echoToolset)
  registerToolset(whoamiToolset)
  registerToolset(tasksToolset)
}
```

`register` may be async, which is what lets a toolset decide its tools at request
time — the PostgREST toolset reads your schema before registering anything.

Set `MCP_TOOLSETS` to a comma-separated list to narrow what one deployment
exposes, for example `MCP_TOOLSETS=postgrest`. The function logs the toolsets it
registered at startup.

## Environment

| Variable                     | Default                  | Purpose                                                       |
| ---------------------------- | ------------------------ | ------------------------------------------------------------- |
| `MCP_PUBLIC_SUPABASE_URL`    | Hosted project URL       | Public API origin used in OAuth metadata and token audiences   |
| `MCP_SERVER_NAME`            | `supabase-mcp`           | Protocol-level server name returned to MCP clients             |
| `MCP_SERVER_DESCRIPTION`     | Generic sentence         | Server instructions sent to clients                            |
| `MCP_ALLOW_FIRST_PARTY_JWT`  | `true`                   | Accept Supabase user JWTs in addition to OAuth tokens          |
| `MCP_TOOLSETS`               | unset (all)              | Comma-separated toolsets to register                           |

## Deploy

```bash
supabase db push
supabase config push
supabase functions deploy mcp-server
```

No URL secret is required for the standard hosted project URL.
`MCP_PUBLIC_SUPABASE_URL` is only needed when the externally reachable origin
differs from the URL injected into the function, such as local Docker or a
custom proxy domain.
