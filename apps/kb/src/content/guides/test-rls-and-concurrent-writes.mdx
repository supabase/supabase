Two kinds of bugs often pass manual testing and reach production:

- A Row Level Security (RLS) policy that lets user B read or change user A's rows.
- Two requests that arrive at the same moment and both pass a check, so the last seat sells twice or a coupon is redeemed twice.

Clicking through your app as one user triggers neither of them. This guide shows how to reproduce each bug on your local database, fix it, and keep a pgTAP test that runs with `supabase test db` on every pull request.

For the basics of testing a policy with pgTAP, see [Test Row Level Security policies with pgTAP](/docs/guides/database/postgres/testing-row-level-security). This guide builds on it with cross-user cases, column changes, and concurrent writes.

## Prerequisites

- The [Supabase CLI](/docs/guides/local-development/cli/getting-started) and a container runtime
- A local stack started with `supabase start`
- `psql`, to reproduce the race by hand
- Node.js, only for the optional client-side test

## What the Advisors check and what tests add

The [Security and Performance Advisors](/docs/guides/observability/advisors) read your schema and settings. They catch structural problems such as:

- A table in an exposed schema with RLS turned off
- A write policy whose condition is always true, such as `with check (true)`
- A view that bypasses RLS because it runs with its owner's privileges
- A function with a mutable `search_path`
- A policy that calls `auth.uid()` once per row instead of once per query

Run them locally with `supabase db advisors`. Add `--fail-on warn` to make the command exit with an error when it finds a warning, so it can fail a CI job.

The Advisors don't sign in as two users or send two requests at once. They can't tell whether a policy matches what you meant. With both RLS bugs from the next section in place, `supabase db advisors` reports no warnings for the `documents` table. Behavior tests cover that gap:

| Problem                                 | Caught by the Advisors | Caught by                               |
| :-------------------------------------- | :--------------------- | :-------------------------------------- |
| RLS turned off on a table in `public`   | Yes                    | `supabase db advisors`                  |
| A policy checks the wrong team or owner | No                     | A two-user pgTAP test                   |
| A user changes a column they shouldn't  | No                     | A column privilege test                 |
| Two requests both pass a check          | No                     | A two-session test or a constraint test |

## Test that user B can't touch user A's rows

The example is a team app. Users belong to teams, and every document belongs to a team. A user should only read and add documents in their own teams.

### Create the schema

1. Create a migration:

   ```bash
   supabase migration new team_documents
   ```

2. In the new migration file, add the following SQL. The policies contain two bugs that are common in generated code. Both look reasonable when you read them:

   ```sql
   create table public.teams (
     id bigint generated by default as identity primary key,
     name text not null
   );

   create table public.team_members (
     team_id bigint not null references public.teams on delete cascade,
     user_id uuid not null references auth.users on delete cascade,
     primary key (team_id, user_id)
   );

   create table public.documents (
     id bigint generated by default as identity primary key,
     team_id bigint not null references public.teams on delete cascade,
     owner_id uuid not null default auth.uid() references auth.users on delete cascade,
     body text not null
   );

   create index on public.team_members (user_id);
   create index on public.documents (team_id);
   create index on public.documents (owner_id);

   alter table public.teams enable row level security;
   alter table public.team_members enable row level security;
   alter table public.documents enable row level security;

   create policy "Users can see their own memberships"
   on public.team_members for select
   to authenticated
   using (user_id = (select auth.uid()));

   create policy "Members can see their teams"
   on public.teams for select
   to authenticated
   using (
     exists (
       select 1 from public.team_members m
       where m.team_id = teams.id
         and m.user_id = (select auth.uid())
     )
   );

   -- Bug 1: checks that the user is in *a* team, not in this document's team
   create policy "Members can read team documents"
   on public.documents for select
   to authenticated
   using (
     exists (
       select 1 from public.team_members m
       where m.user_id = (select auth.uid())
     )
   );

   -- Bug 2: checks the author, but not that the author belongs to the team
   create policy "Members can add documents"
   on public.documents for insert
   to authenticated
   with check (owner_id = (select auth.uid()));

   create policy "Authors can edit their documents"
   on public.documents for update
   to authenticated
   using (owner_id = (select auth.uid()));

   create policy "Authors can delete their documents"
   on public.documents for delete
   to authenticated
   using (owner_id = (select auth.uid()));
   ```

3. Apply the migration to your local database:

   ```bash
   supabase migration up
   ```

### Write the two-user test

1. Create a test file:

   ```bash
   supabase test new documents_rls
   ```

2. In `supabase/tests/documents_rls_test.sql`, add the following test. It creates two users in two teams, then runs every operation as user B against user A's data:

   ```sql
   begin;
   create extension if not exists pgtap with schema extensions;
   select plan(7);

   -- Two users, each in their own team, each with one document
   insert into auth.users (id, email) values
     ('aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa', 'user-a@example.com'),
     ('bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb', 'user-b@example.com');

   insert into public.teams (id, name) values (101, 'Team A'), (102, 'Team B');

   insert into public.team_members (team_id, user_id) values
     (101, 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa'),
     (102, 'bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb');

   insert into public.documents (id, team_id, owner_id, body) values
     (1001, 101, 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa', 'Team A plan'),
     (1002, 102, 'bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb', 'Team B plan');

   -- Act as user B
   set local role authenticated;
   set local request.jwt.claims = '{"sub": "bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb", "role": "authenticated"}';

   select results_eq(
     'select body from public.documents',
     array['Team B plan'],
     'B sees only Team B documents'
   );

   select throws_ok(
     $$insert into public.documents (team_id, body) values (101, 'planted by B')$$,
     '42501',
     null,
     'B cannot add a document to Team A'
   );

   select is_empty(
     $$update public.documents set body = 'changed by B' where id = 1001 returning id$$,
     'B cannot edit a Team A document'
   );

   select is_empty(
     $$delete from public.documents where id = 1001 returning id$$,
     'B cannot delete a Team A document'
   );

   -- Act as user A, and check that nothing B tried got through
   set local request.jwt.claims = '{"sub": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa", "role": "authenticated"}';

   select results_eq(
     'select body from public.documents',
     array['Team A plan'],
     'A sees only Team A documents, unchanged'
   );

   -- Signed-out visitors see nothing
   set local role anon;
   set local request.jwt.claims = '{"role": "anon"}';

   select is_empty(
     'select 1 from public.documents',
     'anon sees no documents'
   );

   select is_empty(
     'select 1 from public.team_members',
     'anon sees no memberships'
   );

   select * from finish();
   rollback;
   ```

A few details make this test useful:

- `set local role` and `set local request.jwt.claims` make the statements that follow run as that user, the way the Data API runs a signed-in request. `auth.uid()` reads the `sub` claim.
- RLS doesn't raise an error when it hides a row from an `update` or `delete`. The statement succeeds and changes nothing. The test adds `returning id` and checks that no rows come back.
- The test also checks what each user should see. A policy that blocks everything passes every "B cannot" check, so the positive checks guard against that.
- The file runs in one transaction and rolls back, so the test data never persists.

### Run the test and fix the policies

1. Run the tests:

   ```bash
   supabase test db
   ```

   Both bugs show up as failures:

   ```text
   # Failed test 1: "B sees only Team B documents"
   #     Results differ beginning at row 1:
   #         have: ("Team A plan")
   #         want: ("Team B plan")
   # Failed test 2: "B cannot add a document to Team A"
   #       caught: no exception
   #       wanted: 42501
   # Failed test 5: "A sees only Team A documents, unchanged"
   #     Results differ beginning at row 2:
   #         have: ("Team B plan")
   #         want: NULL
   # Looks like you failed 3 tests of 7
   ```

2. Create a migration for the fix:

   ```bash
   supabase migration new fix_document_policies
   ```

3. Add the following SQL. Both policies now check membership in the document's own team:

   ```sql
   drop policy "Members can read team documents" on public.documents;
   drop policy "Members can add documents" on public.documents;

   create policy "Members can read team documents"
   on public.documents for select
   to authenticated
   using (
     exists (
       select 1 from public.team_members m
       where m.team_id = documents.team_id
         and m.user_id = (select auth.uid())
     )
   );

   create policy "Members can add documents"
   on public.documents for insert
   to authenticated
   with check (
     owner_id = (select auth.uid())
     and exists (
       select 1 from public.team_members m
       where m.team_id = documents.team_id
         and m.user_id = (select auth.uid())
     )
   );
   ```

4. Apply the migration and run the tests again:

   ```bash
   supabase migration up
   supabase test db
   ```

   ```text
   All tests successful.
   Result: PASS
   ```

### Optional: run the same check through supabase-js

The pgTAP test runs inside the database. To check the full path through the Data API, sign in two users with two separate clients. This Vitest file needs `@supabase/supabase-js` and `vitest`. Set `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SECRET_KEY` to the `API_URL`, `PUBLISHABLE_KEY`, and `SECRET_KEY` values that `supabase status -o env` prints.

```ts
import { randomUUID } from 'node:crypto'
import { createClient, type SupabaseClient } from '@supabase/supabase-js'
import { beforeAll, describe, expect, it } from 'vitest'

const url = process.env.SUPABASE_URL!
const publishableKey = process.env.SUPABASE_PUBLISHABLE_KEY!
const admin = createClient(url, process.env.SUPABASE_SECRET_KEY!)

// Creates a confirmed user in their own team and returns a client signed in as them
async function signedInMember() {
  const email = `test-${randomUUID()}@example.com`
  const password = randomUUID()
  const { data: created, error } = await admin.auth.admin.createUser({
    email,
    password,
    email_confirm: true,
  })
  if (error) throw error

  const { data: team } = await admin.from('teams').insert({ name: email }).select().single()
  await admin.from('team_members').insert({ team_id: team!.id, user_id: created.user.id })

  const client = createClient(url, publishableKey, { auth: { persistSession: false } })
  const { error: signInError } = await client.auth.signInWithPassword({ email, password })
  if (signInError) throw signInError
  return { client, teamId: team!.id as number }
}

describe('documents: user B against user A', () => {
  let a: SupabaseClient
  let b: SupabaseClient
  let teamA: number
  let docId: number

  beforeAll(async () => {
    ;({ client: a, teamId: teamA } = await signedInMember())
    ;({ client: b } = await signedInMember())

    const { data, error } = await a
      .from('documents')
      .insert({ team_id: teamA, body: 'Team A plan' })
      .select()
      .single()
    if (error) throw error
    docId = data.id
  })

  it('B cannot read A’s document', async () => {
    const { data, error } = await b.from('documents').select().eq('id', docId)
    expect(error).toBeNull()
    expect(data).toEqual([])
  })

  it('B cannot add a document to A’s team', async () => {
    const { error } = await b.from('documents').insert({ team_id: teamA, body: 'planted by B' })
    expect(error?.code).toBe('42501')
  })

  it('B cannot edit or delete A’s document', async () => {
    // RLS hides the row, so these succeed with zero rows. Check the rows, not the error.
    const updated = await b.from('documents').update({ body: 'changed' }).eq('id', docId).select()
    expect(updated.error).toBeNull()
    expect(updated.data).toEqual([])

    const deleted = await b.from('documents').delete().eq('id', docId).select()
    expect(deleted.data).toEqual([])
  })

  it('A still sees the original document', async () => {
    const { data } = await a.from('documents').select('body').eq('id', docId).single()
    expect(data?.body).toBe('Team A plan')
  })
})
```

Each test run creates new users and teams with random emails, so runs don't collide with each other.

### Test the columns a user can change

RLS decides which rows a user can change, not which columns. If users can update their own profile, they can also update every other column in that row. In this example, that includes their own `plan`:

```sql
create table public.profiles (
  id uuid primary key references auth.users on delete cascade,
  display_name text,
  plan text not null default 'free'
);

alter table public.profiles enable row level security;

create policy "Users can see their profile"
on public.profiles for select
to authenticated
using (id = (select auth.uid()));

create policy "Users can edit their profile"
on public.profiles for update
to authenticated
using (id = (select auth.uid()));
```

Supabase grants table privileges to the `anon` and `authenticated` roles by default. To limit which columns users can update, revoke the table-wide `update` and grant it back for the columns users may change:

```sql
revoke update on public.profiles from authenticated, anon;
grant update (display_name) on public.profiles to authenticated;
```

This test fails before the change and passes after it:

```sql
begin;
create extension if not exists pgtap with schema extensions;
select plan(2);

insert into auth.users (id, email)
values ('ffffffff-ffff-ffff-ffff-ffffffffffff', 'profile@example.com');
insert into public.profiles (id, display_name)
values ('ffffffff-ffff-ffff-ffff-ffffffffffff', 'Sam');

set local role authenticated;
set local request.jwt.claims = '{"sub": "ffffffff-ffff-ffff-ffff-ffffffffffff", "role": "authenticated"}';

select results_eq(
  $$update public.profiles set display_name = 'Sam K' returning display_name$$,
  array['Sam K'],
  'a user can rename themselves'
);

select throws_ok(
  $$update public.profiles set plan = 'pro'$$,
  '42501',
  null,
  'a user cannot upgrade their own plan'
);

select * from finish();
rollback;
```

## Test concurrent writes

The second bug needs two sessions. The example is event booking: an event has a number of seats left, and a function books one.

### The check-then-write bug

This function checks the seat count, then writes. It's correct when one person books at a time:

```sql
create table public.events (
  id bigint generated by default as identity primary key,
  name text not null,
  seats_left int not null
);

create table public.bookings (
  id bigint generated by default as identity primary key,
  event_id bigint not null references public.events on delete cascade,
  user_id uuid not null references auth.users on delete cascade
);

create index on public.bookings (event_id);
create index on public.bookings (user_id);

alter table public.events enable row level security;
alter table public.bookings enable row level security;

create policy "Signed-in users can see events"
on public.events for select
to authenticated
using (true);

create policy "Users can see their own bookings"
on public.bookings for select
to authenticated
using (user_id = (select auth.uid()));

-- Check, then write: two calls at the same moment can both pass the check
create function public.book_seat(p_event_id bigint)
returns boolean
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_seats_left int;
begin
  select seats_left into v_seats_left
  from public.events
  where id = p_event_id;

  if v_seats_left is null or v_seats_left < 1 then
    return false;
  end if;

  insert into public.bookings (event_id, user_id)
  values (p_event_id, (select auth.uid()));

  update public.events
  set seats_left = seats_left - 1
  where id = p_event_id;

  return true;
end;
$$;

revoke execute on function public.book_seat from public, anon;
grant execute on function public.book_seat to authenticated;
```

The function is `security definer` so that users can't change `seats_left` directly. They can only book through the function, which always books for `auth.uid()`.

Postgres runs each transaction at the `read committed` isolation level by default. A `select` doesn't see rows that another transaction hasn't committed yet. Two calls that start together both read one seat left, and both book it.

The same bug is easier to hit when app code does the check and the write as two separate requests, such as a supabase-js `select` followed by an `insert`. Nothing ties the two requests together.

### Reproduce the race with two sessions

1. Open two terminals and connect both to the local database:

   ```bash
   psql 'postgresql://postgres:postgres@127.0.0.1:54322/postgres'
   ```

2. In terminal 1, add two users and an event with one seat:

   ```sql
   insert into auth.users (id, email) values
     ('00000000-0000-0000-0000-000000000001', 'race-1@example.com'),
     ('00000000-0000-0000-0000-000000000002', 'race-2@example.com');
   insert into public.events (id, name, seats_left) values (1, 'Launch party', 1);
   ```

3. In terminal 1, book the seat and leave the transaction open:

   ```sql
   begin;
   set local request.jwt.claims = '{"sub": "00000000-0000-0000-0000-000000000001", "role": "authenticated"}';
   select public.book_seat(1);
   ```

   The function returns `t`.

4. In terminal 2, book the same seat:

   ```sql
   begin;
   set local request.jwt.claims = '{"sub": "00000000-0000-0000-0000-000000000002", "role": "authenticated"}';
   select public.book_seat(1);
   ```

   The call waits. Terminal 1 holds a lock on the event row from its `update`.

5. In terminal 1, run `commit;`. Terminal 2 then returns `t`. Run `commit;` in terminal 2.

6. Check the result:

   ```sql
   select seats_left from public.events where id = 1;
   select count(*) from public.bookings where event_id = 1;
   ```

   The event has `-1` seats left and 2 bookings. Session 2 read `seats_left = 1` before it waited for the lock, so it booked anyway.

7. Remove the test rows:

   ```sql
   delete from public.events where id = 1;
   delete from auth.users where email in ('race-1@example.com', 'race-2@example.com');
   ```

### Fix the race

Pick the fix that matches the rule you need to enforce:

| Rule                                      | Fix                                         |
| :---------------------------------------- | :------------------------------------------ |
| A counter must not go below zero          | A conditional `update` and a `check`        |
| You read several values before you decide | A row lock with `select ... for update`     |
| Something may happen at most once         | A unique constraint or partial unique index |

#### Conditional update

Make the check part of the write. The `where` clause runs again on the latest committed row after a lock wait, so only one session can take the last seat:

```sql
create or replace function public.book_seat(p_event_id bigint)
returns boolean
language plpgsql
security definer
set search_path = ''
as $$
begin
  -- The check and the write are one statement. A second caller waits for
  -- the row lock, then re-checks seats_left > 0 against the committed value.
  update public.events
  set seats_left = seats_left - 1
  where id = p_event_id
    and seats_left > 0;

  if not found then
    return false;
  end if;

  insert into public.bookings (event_id, user_id)
  values (p_event_id, (select auth.uid()));

  return true;
end;
$$;

alter table public.events
add constraint events_seats_left_not_negative check (seats_left >= 0);
```

The `check` constraint is a backstop. With it in place, even the original function can't oversell: the second session's `update` fails with a check violation, and its booking rolls back.

#### Row lock

Use `select ... for update` when the decision needs values you read first. The lock makes a second caller wait at the `select` until the first transaction ends. The second caller then reads the committed value:

```sql
create or replace function public.book_seat(p_event_id bigint)
returns boolean
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_seats_left int;
begin
  -- for update locks the event row until this transaction ends.
  -- A second caller waits here, then reads the committed value.
  select seats_left into v_seats_left
  from public.events
  where id = p_event_id
  for update;

  if v_seats_left is null or v_seats_left < 1 then
    return false;
  end if;

  insert into public.bookings (event_id, user_id)
  values (p_event_id, (select auth.uid()));

  update public.events
  set seats_left = seats_left - 1
  where id = p_event_id;

  return true;
end;
$$;
```

The lock only covers one event row, so bookings for other events don't wait.

### Turn the two sessions into a test

pgTAP runs a test file in one session. To test a race, the file opens two more sessions with the [`dblink`](https://www.postgresql.org/docs/current/dblink.html) extension and replays the steps from the previous section. In `supabase/tests/book_seat_race_test.sql`, add:

```sql
begin;
create extension if not exists pgtap with schema extensions;
create extension if not exists dblink with schema extensions;
select plan(3);

-- Open two extra sessions. Their writes commit, so the file cleans up at the end.
do $$
declare
  -- dblink needs a password login, so connect to the address this test came in on
  conn text := format(
    'host=%s dbname=postgres user=postgres password=postgres',
    host(inet_server_addr())
  );
begin
  perform extensions.dblink_connect('s1', conn);
  perform extensions.dblink_connect('s2', conn);

  -- Remove rows a failed earlier run left behind, then add the test rows
  perform extensions.dblink_exec('s1', $sql$
    delete from public.events where id = 9001;
    delete from auth.users where email in ('race-1@example.com', 'race-2@example.com');
    insert into auth.users (id, email) values
      ('cccccccc-cccc-cccc-cccc-cccccccccccc', 'race-1@example.com'),
      ('dddddddd-dddd-dddd-dddd-dddddddddddd', 'race-2@example.com');
    insert into public.events (id, name, seats_left) values (9001, 'Race test', 1);
  $sql$);

  perform extensions.dblink_exec('s1', $sql$
    set role authenticated;
    set request.jwt.claims = '{"sub": "cccccccc-cccc-cccc-cccc-cccccccccccc", "role": "authenticated"}';
  $sql$);
  perform extensions.dblink_exec('s2', $sql$
    set role authenticated;
    set request.jwt.claims = '{"sub": "dddddddd-dddd-dddd-dddd-dddddddddddd", "role": "authenticated"}';
  $sql$);
end $$;

-- Session 1 books the last seat and keeps its transaction open
do $$ begin perform extensions.dblink_exec('s1', 'begin'); end $$;
select ok(
  (select booked from extensions.dblink('s1', 'select public.book_seat(9001)') as t(booked boolean)),
  'session 1 books the last seat'
);

-- Session 2 asks for the same seat while session 1 is still open
do $$
begin
  perform extensions.dblink_send_query('s2', 'select public.book_seat(9001)');

  -- Wait until session 2 is blocked on a lock held by session 1
  for i in 1..50 loop
    perform pg_stat_clear_snapshot();
    exit when exists (
      select 1 from pg_stat_activity
      where query = 'select public.book_seat(9001)'
        and wait_event_type = 'Lock'
    );
    perform pg_sleep(0.1);
  end loop;

  perform extensions.dblink_exec('s1', 'commit');
end $$;

-- fail_on_error => false: an error in session 2 counts as "no seat", not a crash
select ok(
  not coalesce(
    (select booked from extensions.dblink_get_result('s2', false) as t(booked boolean)),
    false
  ),
  'session 2 does not get a seat'
);

select results_eq(
  'select count(*) from public.bookings where event_id = 9001',
  array[1::bigint],
  'the event has exactly one booking'
);

-- Clean up the committed rows and close the sessions
do $$
begin
  perform * from extensions.dblink_get_result('s2', false) as t(booked boolean);
  perform extensions.dblink_exec('s1', $sql$
    reset role;
    delete from public.events where id = 9001;
    delete from auth.users where id in (
      'cccccccc-cccc-cccc-cccc-cccccccccccc',
      'dddddddd-dddd-dddd-dddd-dddddddddddd'
    );
  $sql$);
  perform extensions.dblink_disconnect('s1');
  perform extensions.dblink_disconnect('s2');
end $$;

select * from finish();
rollback;
```

How the test stays reliable:

- It waits until session 2 is blocked on a lock before session 1 commits. The original function and both fixes all reach that lock, so the result doesn't depend on timing. `pg_stat_clear_snapshot()` makes each loop read fresh activity data.
- `dblink` only lets a non-superuser connect with a password. Local connections to `127.0.0.1` don't ask for one, so the test connects to the server address the test session itself used.
- The sessions commit their rows, so the file removes them at the end, and removes leftovers from a failed run at the start.

Against the original function, the test fails:

```text
# Failed test 2: "session 2 does not get a seat"
# Failed test 3: "the event has exactly one booking"
#     Results differ beginning at row 1:
#         have: (2)
#         want: (1)
# Looks like you failed 2 tests of 3
```

With either fix, it passes.

> [!NOTE]
> This test uses the local database password, `postgres`. Run it against your local stack or in CI, not against a hosted project.

### Use a unique index for "at most once" rules

A coupon that each user can redeem once has the same bug in a simpler form. This app code checks for an earlier redemption, then inserts one:

```ts
async function redeemWithCheck(client: SupabaseClient, code: string) {
  const { data: existing } = await client
    .from('coupon_redemptions')
    .select('id')
    .eq('coupon_code', code)
    .is('refunded_at', null)
  if (existing && existing.length > 0) return 'already redeemed'
  const { error } = await client.from('coupon_redemptions').insert({ coupon_code: code })
  return error ? error.code : 'redeemed'
}
```

Called twice in parallel with `Promise.all`, both calls can read no earlier redemption before either one inserts. Then both insert, and the user gets the discount twice.

The table:

```sql
create table public.coupon_redemptions (
  id bigint generated by default as identity primary key,
  coupon_code text not null,
  user_id uuid not null default auth.uid() references auth.users on delete cascade,
  refunded_at timestamptz
);

create index on public.coupon_redemptions (user_id);

alter table public.coupon_redemptions enable row level security;

create policy "Users can see their redemptions"
on public.coupon_redemptions for select
to authenticated
using (user_id = (select auth.uid()));

create policy "Users can redeem for themselves"
on public.coupon_redemptions for insert
to authenticated
with check (user_id = (select auth.uid()) and refunded_at is null);
```

Let the database enforce the rule. A partial unique index allows one active redemption per user and coupon. A refunded redemption doesn't count:

```sql
-- One active redemption per user per coupon. A refunded redemption doesn't count.
create unique index coupon_redemptions_one_active
on public.coupon_redemptions (coupon_code, user_id)
where refunded_at is null;
```

When two transactions insert the same key, the second one waits for the first, then fails with error `23505`. Your app can treat `23505` as "already redeemed". Use a plain `unique (coupon_code, user_id)` constraint if a redemption can never be undone.

If your data already has duplicates, creating the index fails. Find them first:

```sql
select coupon_code, user_id, count(*)
from public.coupon_redemptions
where refunded_at is null
group by coupon_code, user_id
having count(*) > 1;
```

The index holds under concurrency, so the test doesn't need two sessions. It checks that the index exists and that it rejects a second redemption:

```sql
begin;
create extension if not exists pgtap with schema extensions;
select plan(4);

select has_index(
  'public', 'coupon_redemptions', 'coupon_redemptions_one_active',
  'redemptions have a unique index'
);

insert into auth.users (id, email)
values ('eeeeeeee-eeee-eeee-eeee-eeeeeeeeeeee', 'coupon@example.com');

set local role authenticated;
set local request.jwt.claims = '{"sub": "eeeeeeee-eeee-eeee-eeee-eeeeeeeeeeee", "role": "authenticated"}';

select lives_ok(
  $$insert into public.coupon_redemptions (coupon_code) values ('LAUNCH50')$$,
  'first redemption works'
);

select throws_ok(
  $$insert into public.coupon_redemptions (coupon_code) values ('LAUNCH50')$$,
  '23505',
  null,
  'second redemption of the same coupon is rejected'
);

-- After a refund, the user can redeem the coupon again
reset role;
update public.coupon_redemptions set refunded_at = now()
where coupon_code = 'LAUNCH50';
set local role authenticated;

select lives_ok(
  $$insert into public.coupon_redemptions (coupon_code) values ('LAUNCH50')$$,
  'redemption works again after a refund'
);

select * from finish();
rollback;
```

## Run the tests on every pull request

`supabase test db` runs every file in `supabase/tests`. To run them in CI, start from the GitHub Actions workflow in [Testing overview](/docs/guides/local-development/testing/overview#continuous-integration-testing), which starts a local stack and runs `supabase test db`. Add `supabase db advisors --fail-on warn` as a step after it, so the job also fails on Advisor warnings.

With [Branching](/docs/guides/deployment/branching), each pull request gets a preview branch built from the migrations in your repository. The CLI can target a branch with `--remote`, for example `supabase test db --remote=<branch>` and `supabase db advisors --remote=<branch>`. Keep the race test in the local CI job, since it uses the local password.

## Checklist before launch

- For every table with user data, a test signs in as user B and tries to `select`, `insert`, `update`, and `delete` user A's rows. The same test checks that user A still sees their own rows.
- Signed-out visitors (`anon`) see only what you meant to make public.
- Columns that users must not change, such as plans, roles, or balances, aren't granted for `update`.
- Every "only N" rule uses a conditional `update` or a row lock, with a `check` constraint as a backstop, and has a two-session test.
- Every "at most once" rule has a unique constraint or partial unique index.
- `supabase db advisors` reports no warnings.

To check more statement orders than the two-session test covers, [VibeRaven](https://github.com/ohad6k/VibeRaven) is an open-source CLI that runs two-user PostgreSQL race tests and replays a failing order. I maintain it.
