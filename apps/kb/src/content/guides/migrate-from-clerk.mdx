Understanding a Clerk-to-Supabase Auth migration helps you choose a cutover approach and plan which user data your app needs to update.

## Overview

A Clerk-to-Supabase Auth migration creates Supabase Auth users from Clerk exports and moves your app to the new identity system. User IDs, sessions, and social sign-ins work differently in each service, so plan how your app will reference users after the move. If you want to keep Clerk as the identity provider, Supabase third-party authentication may let you use Clerk JWTs with supported Supabase services without migrating users.

## How a migration works

A migration has four stages, from choosing a cutover approach to updating application records.

| Stage | What happens |
| --- | --- |
| Plan | Choose a one-time import or a gradual migration while Clerk remains available. |
| Export | Export users from Clerk. Only the Dashboard export includes password digests and time-based one-time password (TOTP) secrets. CLI and Backend API exports include metadata and ban status. |
| Map and import | Map verified emails, phone numbers, metadata, and supported password hashes to Supabase Auth users through the [Auth Admin API](/docs/reference/javascript/admin-api). Before enabling sign-in, identify banned users and apply an equivalent restriction server-side with [`updateUserById()`](/docs/reference/javascript/auth-admin-updateuserbyid) and `ban_duration`. |
| Cut over | Update app records to reference Supabase Auth UUIDs, configure sign-in methods, and plan for users to create Supabase Auth sessions. |

If you need both password digests and metadata, combine a Dashboard export with a CLI or Backend API export by Clerk user ID. Check the exported fields for your chosen method. Clerk's [export guide](https://clerk.com/docs/guides/development/migrating/export-from-clerk) describes what each method includes.

## One-time vs gradual migration

The right approach depends on how much downtime your application can accept and whether you can support two identity systems during the transition.

| Approach | When it fits | Trade-off |
| --- | --- | --- |
| One-time | You can schedule a cutover and pause sign-ups or account changes during the import. | Users move together, but the export can become stale if user data changes before the import finishes. |
| Gradual | You need to keep sign-in available while users move over time. | Your app must implement a migration-on-sign-in flow and keep both systems consistent during the transition. |

## What changes for users

Plan for these differences when you choose a migration date and communicate with users.

| Data or behavior | Migration impact |
| --- | --- |
| User IDs | Supabase Auth user IDs are UUIDs. Preserve a Clerk ID if it is a supported UUID; otherwise map it to a new Supabase Auth ID and update foreign keys and app records. |
| Passwords | Supabase Auth supports bcrypt and Argon2 password hashes through `password_hash`. Users whose hashes use an unsupported algorithm or format, or whose import has no matching Dashboard password digest, need a password reset or another recovery flow. |
| Email and phone verification | Set `email_confirm` or `phone_confirm` only when the corresponding Clerk address was verified. |
| Metadata | Clerk's API exports include metadata. Map profile fields to `user_metadata` and trusted authorization data to `app_metadata`, following [Supabase Auth's user guidance](/docs/guides/auth/users). |
| Sessions and social sign-ins | Clerk sessions are not Supabase Auth sessions, and user exports do not import social account credentials. Configure the required providers in Supabase Auth and plan for users to create Supabase Auth sessions. |
| TOTP | Clerk Dashboard exports include TOTP secrets, but the documented Auth Admin API has no factor-import method. Users have no verified Supabase factor until they enroll a new one. If Clerk TOTP gated sensitive access, decide how your app will restrict that access or require trusted re-verification until enrollment. |

## When to keep Clerk

You can keep Clerk as your identity provider and use its JWTs with supported Supabase services through [third-party authentication](/docs/guides/auth/third-party/clerk). This avoids moving accounts to Supabase Auth, which is a separate migration path.
