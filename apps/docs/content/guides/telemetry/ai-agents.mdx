AI agents can monitor and debug Supabase projects using the MCP server and the `supabase` skill. The skill uses a **docs-first architecture**: instead of embedding cause-and-fix content that becomes stale, it routes the agent to the current guide for the specific symptom.

## Setup

1. Install the [Supabase MCP server](/docs/guides/getting-started/mcp).
2. Add the `supabase` skill: `npx skills add supabase`.

Once installed, the agent can debug failing requests, query logs, run advisors, and apply fixes — routing to the guides in this section for the source of truth on each issue.

## MCP tools for observability

The Supabase MCP server exposes several tools relevant to monitoring and debugging:

| Tool           | Description                                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `get_logs`     | Query logs for a project by service name and time window. Engine-agnostic — works across ClickHouse and BigQuery projects. |
| `get_advisors` | Run the Supabase security and performance advisors against a project.                                                      |
| `execute_sql`  | Run a SQL query directly against the database.                                                                             |
| `search_docs`  | Search Supabase documentation by keyword or error string.                                                                  |

### Querying logs with `get_logs`

`get_logs` takes a service name (`auth`, `edge`, `postgres`, `storage`, `realtime`, `functions`) and an optional time window. It is the primary log-querying path for agents because it is engine-agnostic and does not require knowledge of the ClickHouse or BigQuery query model.

When `get_logs` returns an empty result, widen along an anchor — a timestamp, request ID, or error code — rather than broadening the service scope.

For cases where raw SQL is needed (field-level filtering, aggregation), use the `execute_sql` tool against the [Logs Explorer endpoint](/docs/guides/telemetry/logs). The [Logging guide](/docs/guides/telemetry/logs) covers ClickHouse syntax.

## The debugging skill

The `supabase` skill's debugging workflow follows the same loop as the [Debugging guide](/docs/guides/telemetry/debugging):

1. Read the error precisely — status code, error code, full message.
2. Locate the failing layer using the request-stack model.
3. Query that layer's logs using `get_logs` with a bounded time window.
4. Fetch the troubleshooting guide for the specific symptom (append `.md` to the docs URL, or use `search_docs`).
5. Apply the fix, then verify by re-running the failing operation.

The skill routes to the [symptom-to-layer table](/docs/guides/telemetry/debugging#find-the-guide-for-your-symptom) rather than embedding cause-and-fix content. This means the agent uses current documentation and the skill stays stable as the docs evolve.
