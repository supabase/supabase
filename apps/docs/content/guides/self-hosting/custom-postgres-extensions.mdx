## Overview

The `supabase/postgres` image ships a curated set of extensions that are compiled in at build time. There is **no runtime mechanism to install a compiled (native `.so`) extension** into a running container: you cannot `apk add` or `apt-get install` an extension package, because the image is built with [Nix](https://nixos.org) and its extension set is fixed when the image is produced.

To add a native extension that Supabase doesn't bundle, you build a **custom image** that layers the extension on top of the official one. This guide walks through that end to end for the current Alpine-based images (the Debian-to-Alpine switch landed at tag `17.6.1.083`), using [`pg_uuidv7`](https://github.com/fboulnois/pg_uuidv7) as the running example.

<Admonition type="note">

If your extension is written in **pure SQL or a trusted procedural language** (no native code), you don't need a custom image at all. Use [`pg_tle`](https://github.com/aws/pg_tle), which is preloaded and enabled by default. This guide is for extensions that ship a compiled `.so`.

</Admonition>

<Admonition type="tip">

If the extension's maintainer already publishes a prebuilt Supabase Postgres image with the extension baked in, just point your `db` service at that image - it's less work than building your own. This guide is for when no prebuilt image exists.

</Admonition>

The _proper_ way to add an extension is to compile it into the image's [Nix build](#alternative-build-the-extension-into-the-nix-image), so it's built with the same toolchain as everything else. That's the most robust route, but it's involved - it needs Nix, building the image from source, and maintaining a fork. If that's heavier than you want, the rest of this guide is a lighter-weight alternative: build just your extension in an ordinary Docker builder and layer it onto the published image. The approach can work for many standard [PGXS](https://www.postgresql.org/docs/current/extend-pgxs.html) extensions - but since it cuts against the way the image is meant to be assembled, your mileage may vary, and the constraints in the next section are the trade-off.

### Why these images need special handling

The image is Alpine Linux, but the PostgreSQL binaries and every bundled extension live in a `/nix` store. Three facts drive every step below:

1. **The runtime is glibc, not musl.** Even though the base OS is Alpine (which uses musl libc), the Nix-built `postgres` and its extensions are linked against **glibc**. If you compile an extension with Alpine's native toolchain (`apk add build-base`), it links musl and **fails to load** at `CREATE EXTENSION` with an error like `libc.musl-aarch64.so.1: cannot open shared object file`. You must build in a **glibc** environment.
2. **Match the major version, and keep the builder's glibc no newer than the image's.** Extensions are ABI-stable across an entire Postgres major version, so _any_ 17.x builder works against _any_ 17.x image - the **minor** version doesn't matter (a build against 17.10 loads fine on 17.6). What _does_ matter is glibc: a `.so` built against a **newer** glibc than the runtime provides fails to load (`version 'GLIBC_2.xx' not found`). The Supabase image currently ships **glibc 2.40**, so this guide builds on **Debian bookworm** (`postgres:17-bookworm`, glibc 2.36), which stays safely below it. Avoid the default `postgres:17` tag, which is currently Debian trixie (glibc 2.41 - _newer_ than the runtime).
3. **The module directory is redirected.** The running `postgres` is a wrapper script that overrides its library directory via a `NIX_PGLIBDIR` environment variable. Your compiled `.so` must be installed into that directory - _not_ the path `pg_config --pkglibdir` reports. This is why you can't just follow an extension's upstream install instructions (which typically use `make install` or copy to `pg_config --pkglibdir`): on these images `$libdir` resolves to `NIX_PGLIBDIR`, so a `.so` placed in `pkglibdir` loads with `could not access file "$libdir/<name>"`.

The cleanest way to satisfy 1 and 2 is to compile inside a glibc `postgres:<major>-bookworm` image and then copy the artifacts into the Supabase runtime image.

<Admonition type="note" title="How the image is versioned">

The tag starts with the PostgreSQL version (`17.6`) followed by Supabase's own release numbers - so `17.6.1.136` is **PostgreSQL 17.6** (the trailing `.1.136` is Supabase's versioning, not part of the Postgres version). Every tag beginning `17.6` is the same Postgres version; only Supabase's build number changes. Because extension ABI is stable across a major version, you don't need to match the minor - but if a future image bumps its glibc, re-check the rule in point 2. You can read the image's glibc version with:

```sh
docker run --rm --entrypoint sh supabase/postgres:17.6.1.136 -c \
  'ls -d /nix/store/*glibc-2.*-* 2>/dev/null | grep -oE "glibc-2\.[0-9]+" | sort -uV | tail -1'
# -> glibc-2.40
```

</Admonition>

## Prerequisites

- Docker installed and running
- The exact `supabase/postgres` tag your deployment uses (see `db.image` in your `docker-compose.yml`, e.g. `supabase/postgres:17.6.1.136`)
- Extension source that builds with standard [PGXS](https://www.postgresql.org/docs/current/extend-pgxs.html)

<Admonition type="caution">

Always build against the **same major version** you run, and rebuild your custom image whenever you upgrade the base image.

</Admonition>

## Step 1: Write the Dockerfile

Use a multi-stage build: a **glibc builder** stage (`postgres:<major>-bookworm`) to compile, and the **Supabase image** as the runtime stage that installs the artifacts into the correct Nix locations.

The example below builds [`pg_uuidv7`](https://github.com/fboulnois/pg_uuidv7) (UUIDv7 generation - a commonly requested extension that isn't in the default build) straight from its Git repository.

```dockerfile name=Dockerfile
# syntax=docker/dockerfile:1
ARG SUPABASE_POSTGRES_TAG=17.6.1.136
ARG PG_MAJOR=17

# --- Builder: glibc image matching the Postgres major version ---
FROM postgres:${PG_MAJOR}-bookworm AS builder
ARG PG_MAJOR
ARG EXT_VERSION=v1.7.0
RUN apt-get update && apt-get install -y --no-install-recommends \
      build-essential git ca-certificates postgresql-server-dev-${PG_MAJOR} \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
RUN git clone --depth 1 --branch ${EXT_VERSION} https://github.com/fboulnois/pg_uuidv7 .
RUN make

# --- Runtime: Supabase Alpine image ---
FROM supabase/postgres:${SUPABASE_POSTGRES_TAG}
USER root
COPY --from=builder /src/pg_uuidv7.so      /tmp/
COPY --from=builder /src/pg_uuidv7.control /tmp/
COPY --from=builder /src/sql/              /tmp/ext-sql/
# The running postgres wrapper redirects its module dir via NIX_PGLIBDIR.
# Install the .so there; install control/SQL into pg_config --sharedir.
RUN set -eux; \
    PLUGIN_DIR="$(grep -E '^export NIX_PGLIBDIR' /usr/bin/postgres | sed -E "s/.*'([^']*)'.*/\1/")"; \
    SHARE_DIR="$(pg_config --sharedir)/extension"; \
    install -m 755 /tmp/pg_uuidv7.so "$PLUGIN_DIR/"; \
    install -m 644 /tmp/pg_uuidv7.control "$SHARE_DIR/"; \
    install -m 644 /tmp/ext-sql/*.sql "$SHARE_DIR/"; \
    rm -rf /tmp/pg_uuidv7.* /tmp/ext-sql
```

Building your own extension? The same Dockerfile works - just `COPY` your PGXS source into the builder instead of `git clone`. If you're authoring a _new_ extension from scratch, add it to the Nix build instead (see [Alternative: build the extension into the Nix image](#alternative-build-the-extension-into-the-nix-image) below).

### Handle dependencies beyond libc

Copying a `.so` onto the image works cleanly only when its **sole** runtime dependency is libc - libc is already loaded in the `postgres` process, so it resolves for free. Any _other_ shared library the extension links (libcurl, OpenSSL, etc.) must also be present **and findable** at runtime. Because the image is Nix-built, it has no `ld.so.cache` and no glibc libraries under `/usr/lib` - Nix resolves each binary's dependencies through a per-binary `RUNPATH` into the store instead - so a Debian-built `.so`, which relies on the usual library search, won't find them and `CREATE EXTENSION` fails with `libX.so: cannot open shared object file`.

The build happens inside Docker, so check the compiled `.so` in the builder stage rather than on your host (`readelf` is already available there via `build-essential`):

```sh
# build only the builder stage, then inspect the .so it produced
docker build --target builder -t ext-builder .
docker run --rm --entrypoint sh ext-builder -c 'readelf -d /src/*.so | grep NEEDED'
```

- **Only `libc.so.6` and `ld-linux-*`** → you're done; the Dockerfile above is sufficient (`pg_uuidv7` is this case).
- **Anything else listed** → handle those dependencies with one of the options below.

**Recommended: statically link the extra dependencies** into the `.so`, so its only remaining `NEEDED` is libc (keep libc itself dynamic - never statically link glibc). After building, re-run the check above and confirm only `libc.so.6` and `ld-linux-*` remain.

A few things make this more involved than it sounds:

- **The distro's own static archive is often not enough.** A feature-rich `libcurl.a`, for example, drags in a large transitive chain (HTTP/2, IDN, brotli, SSH…) whose static archives aren't all installable - so you typically build a _minimal_ static version of the dependency from source and link that, forcing the static archives (`-l:libfoo.a`).
- **PGXS may ignore the extension's `CFLAGS`.** Pass extra include paths via `PG_CPPFLAGS` on the `make` command line rather than editing the Makefile.
- **Static linking has limits.** It won't help a dependency that `dlopen`s plugins at runtime, and linking a library that's _also_ loaded by another extension (two copies of OpenSSL in one process, say) can clash.
- **Some extensions hard-code their own name**, so you can't rename one to sidestep a collision with a bundled extension.

When static linking isn't practical, use the [Nix path](#alternative-build-the-extension-into-the-nix-image), which resolves every dependency against the image's own libraries automatically.

## Step 2: Build the image

Build against the tag you run in production so the runtime and major version match:

```sh
docker build \
  --build-arg SUPABASE_POSTGRES_TAG=17.6.1.136 \
  --build-arg PG_MAJOR=17 \
  -t myorg/supabase-postgres-custom:17.6.1.136 \
  .
```

## Step 3: Use the image in your stack

Point the `db` service at your custom image in `docker-compose.yml`:

```yaml name=docker-compose.yml
db:
  image: myorg/supabase-postgres-custom:17.6.1.136
  # ...leave the rest of the service definition unchanged
```

Or build it as part of the stack with a `build:` block instead of `image:`:

```yaml name=docker-compose.yml
db:
  # replace the `image:` line with this; leave the rest of the service unchanged
  build:
    context: ./my-extension
    args:
      SUPABASE_POSTGRES_TAG: 17.6.1.136
      PG_MAJOR: '17'
```

Then recreate the database service so it picks up the new image:

```sh
sh run.sh recreate db
```

## Step 4: Enable the extension

The Supabase `postgres` role is intentionally **not a superuser**, and extension creation is gated by [`supautils`](https://github.com/supabase/supautils). A native extension that isn't on the `supautils.privileged_extensions` allow-list can only be created by the `supabase_admin` superuser. You have two options.

### Option A: Allow the `postgres` role to create it (no rebuild)

The Postgres 17 image loads any `.conf` file from `/etc/postgresql-custom/conf.d/`, and that directory is included **after** the baked-in `supautils.conf`, so a `conf.d` file wins. Append your extension to the allow-list there. Because the list has no "append" syntax, restate the current value plus your extension:

```sh
docker exec supabase-db bash -c '
CUR=$(psql -U postgres -tAc "show supautils.privileged_extensions" | tr -d "\n")
cat > /etc/postgresql-custom/conf.d/99-custom-extensions.conf <<EOF
supautils.privileged_extensions = '"'"'$CUR, pg_uuidv7'"'"'
EOF'
```

Restart to apply, then create it as the regular `postgres` role:

```sh
sh run.sh restart db
docker compose exec db psql -U postgres -c "CREATE EXTENSION pg_uuidv7;"
```

<Admonition type="note">

`/etc/postgresql-custom/` is on the `db-config` named volume, so this change persists across restarts. See [Custom Postgres configuration](/guides/self-hosting/postgres-upgrade-17#custom-postgres-configuration) for more on the `conf.d/` mechanism.

</Admonition>

### Option B: Enable it as a superuser

The image's init scripts run as `supabase_admin` (a superuser) on first boot. Drop a SQL file into the init directory to create the extension automatically for **new** databases:

```yaml name=docker-compose.yml
db:
  volumes:
    # ...keep the existing mounts (the data dir, roles.sql, etc.) and add:
    - ./volumes/db/pg_uuidv7.sql:/docker-entrypoint-initdb.d/migrations/99-pg_uuidv7.sql:Z
```

```sql name=volumes/db/pg_uuidv7.sql
CREATE EXTENSION IF NOT EXISTS pg_uuidv7;
```

<Admonition type="caution">

Init scripts only run when the data directory (`./volumes/db/data`) is **empty**, i.e. on first initialization. For an already-initialized database, connect as `supabase_admin` once and run `CREATE EXTENSION` manually.

</Admonition>

## Verify

```sh
docker compose exec db psql -U postgres \
  -c "CREATE EXTENSION IF NOT EXISTS pg_uuidv7;" \
  -c "SELECT uuid_generate_v7();"
```

## Extensions that need preloading

If your extension must be listed in `shared_preload_libraries` (for example, one that runs a background worker), add it with the same `conf.d/` mechanism. The `conf.d/` include runs after the baked-in setting, so restate the current value plus your library:

```sh
docker exec supabase-db bash -c '
CUR=$(psql -U postgres -tAc "show shared_preload_libraries" | tr -d "\n")
cat > /etc/postgresql-custom/conf.d/99-preload.conf <<EOF
shared_preload_libraries = '"'"'$CUR, my_bgworker'"'"'
EOF'
sh run.sh restart db
```

<Admonition type="caution">

`shared_preload_libraries` has no append syntax - you must restate the **full** existing list plus your library, or you'll disable the extensions Supabase relies on. A restart (not a reload) is required.

</Admonition>

## Alternative: build the extension into the Nix image

The Docker approach above layers a separately-compiled `.so` onto the published image. The alternative is to add the extension to Supabase's own [Nix](https://nixos.org) build, so it's compiled with the exact same toolchain as everything else in the image. This is the most robust option - it sidesteps the libc/ABI concerns entirely and is how the bundled extensions are built - but it requires Nix, building the image from source, and maintaining a fork of `supabase/postgres`.

Rough guide to choosing:

- **One-off extension on the stock image, minimal tooling** → the Docker approach in this guide.
- **Bulletproof ABI match, want it upstreamed, or it needs preload / `supautils` wiring done "the Supabase way"** → the Nix build below.

This guide intentionally doesn't teach Nix. The authoritative, maintained instructions live in the `supabase/postgres` repository:

- [Adding a new extension package](https://github.com/supabase/postgres/blob/develop/nix/docs/adding-new-package.md) - the main walkthrough (C/C++ and Rust/pgrx patterns, where to register the extension, generating hashes)
- [Creating a pgrx extension](https://github.com/supabase/postgres/blob/develop/nix/docs/creating-pgrx-extension.md) - for Rust extensions
- [Building Postgres](https://github.com/supabase/postgres/blob/develop/nix/docs/build-postgres.md) and the full [`nix/docs`](https://github.com/supabase/postgres/tree/develop/nix/docs) directory

<Admonition type="note">

These steps are maintained in the `supabase/postgres` repo, not here. Follow that repository for the current process.

</Admonition>

## Keeping the image up to date

Because your image is pinned to a specific `supabase/postgres` tag and depends on that build's internal Nix paths, treat it as coupled to the base image:

- Rebuild with the new `SUPABASE_POSTGRES_TAG` (and matching `PG_MAJOR`) every time you upgrade Postgres.
- Re-test `CREATE EXTENSION` after each rebuild. A change to the base OS or Nix layout - as happened when the images moved from Debian to Alpine - can require adjusting the build.
