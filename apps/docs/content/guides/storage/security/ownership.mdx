Storage records an owner for every bucket and object. Knowing the owner lets you write access rules scoped to that user. For how to write those rules, see [Storage access control](/docs/guides/storage/security/access-control).

When you create a bucket or object in Supabase Storage, Storage assigns it an owner automatically. The owner is the user who created the resource, taken from the `sub` claim in the JWT. Storage keeps the owner in the `owner_id` column.

The [Storage schema](/docs/guides/storage/schema/design) has two fields to represent ownership: `owner` and `owner_id`. `owner` is deprecated. Use `owner_id` instead.

<Admonition type="note">

When you create a resource with the `service_key`, Storage doesn't set an owner, and the resource is owned by anyone. The same applies to Storage resources you create in the Dashboard.

</Admonition>

## Access control

Ownership by itself provides no access control. To enforce it, scope access control on Storage resources to their owner.

For example, you can implement a policy where only the owner of an object can delete it. To do this, check the `owner_id` field of the object and compare it with the `sub` claim of the JWT:

```sql
create policy "User can delete their own objects"
on storage.objects
for delete
to authenticated
using (
    owner_id = (select auth.uid()::text)
);
```

Row Level Security (RLS) policies are one way to enforce access control. You can also implement access control in your server code by following the same pattern.
