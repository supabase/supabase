Knowing how the Storage cache works tells you why a first request is slower than the next one, and why public buckets cache better than private buckets. For how to remove an object from the cache, see [Purge CDN cache](/docs/guides/storage/cdn/purge-cdn-cache).

All assets uploaded to Supabase Storage are cached on a Content Delivery Network (CDN) to improve the latency for users all around the world. CDNs are a geographically distributed set of servers or _nodes_ which cache content from an _origin server_. For Supabase Storage, the origin is the storage server running in the [same region as your project](/dashboard/project/_/settings/general). Aside from performance, CDNs also help with security and availability by mitigating Distributed Denial of Service (DDoS) and other application attacks.

## How caching works

The following example shows how a CDN helps with performance.

A new bucket is created for a Supabase project launched in Singapore. All requests to the Supabase Storage API are routed to the CDN first.

A user from the United States requests an object and is routed to the U.S. CDN. At this point, that CDN node does not have the object in its cache and pings the origin server in Singapore.
![Sequence diagram of a cache miss. The client sends a request to the Supabase CDN, which forwards it to the Supabase Storage server. The server returns the asset, the CDN caches it, and the CDN sends the response to the client.](/docs/img/cdn-cache-miss.png)

Another user, also in the United States, requests the same object and is served directly from the CDN cache in the United States instead of routing the request back to Singapore.
![Sequence diagram of a cache hit. The client sends a request to the Supabase CDN, which responds from its cache. The request never reaches the Supabase Storage server.](/docs/img/cdn-cache-hit.png)

<Admonition type="note">

A CDN can still evict your object from its cache if no one in a region has requested it for a while. For example, if no user in the United States requests your object, the U.S. CDN node removes it from its cache, even with a long cache-control duration.

</Admonition>

The cache status of a particular request is sent in the `cf-cache-status` header. A cache status of `MISS` indicates that the CDN node did not have the object in its cache and had to ping the origin to get it. A cache status of `HIT` indicates that the object was sent directly from the CDN.

## Public vs private buckets

Objects in public buckets don't require authorization to access. This leads to a better cache hit rate compared to private buckets.

For private buckets, Storage checks the permissions for each object per user. For example, if two different users access the same object in a private bucket from the same region, it results in a cache miss for both users. The users might have different security policies attached to them.
On the other hand, if two different users access the same object in a public bucket from the same region, it results in a cache hit for the second user.
