This guide explains how to use the sources in [Observe the data](/docs/guides/observability/access-data) to notice that something is wrong. You want a count, a rate, or a finding, not a root cause.

Use this page to run a [Health](#health), [Security](#security), [Performance](#performance), or [Usage](#usage) check. Already have an error message, HTTP status, SQLSTATE, or a clear advisor finding? Skip straight to [Diagnosing](/docs/guides/troubleshooting).

## Use the sources [#notice-a-signal]

Run a coarse check against the sources in [Observe the data](/docs/guides/observability/access-data). How to access each source lives there. The queries below show what to look for.

If a check turns up a spike, a named error, or an advisor finding, take it to [Diagnosing](/docs/guides/troubleshooting). If the result is only a count, narrow the time window and pick one identifier (path, status, SQLSTATE, request ID) first.

### Health

Ask whether API error rates or availability are off.

Count API 5xx responses by path. Compare the count to the last quiet window.

```sql
-- api 5xx by path
select
  log_attributes['request.path'] as path,
  count() as errors
from logs
where source = 'edge_logs'
  and toInt32OrZero(log_attributes['response.status_code']) >= 500
group by path
order by errors desc
limit 20;
```

You can also read the same signal on [Reports](/docs/guides/observability/reports) (API response errors) without writing SQL. Check connection pressure with [`supabase inspect db role-connections`](/docs/reference/cli/supabase-inspect-db-role-connections), or scrape CPU and connection series from the [Metrics API](/docs/guides/observability/metrics).

### Security

Ask whether advisors or authorization failures need review.

Pull [Security Advisor](/docs/guides/observability/advisors) findings from Studio, MCP `get_advisors`, the CLI, or the Management API. Then count API 401 and 403 responses by path.

```sql
-- api 401 and 403 by path
select
  log_attributes['request.path'] as path,
  toInt32OrZero(log_attributes['response.status_code']) as status,
  count() as events
from logs
where source = 'edge_logs'
  and toInt32OrZero(log_attributes['response.status_code']) in (401, 403)
group by path, status
order by events desc
limit 20;
```

Read a finding together with the matching log window. Advisors are not a substitute for error rates. Auth error charts in [Reports](/docs/guides/observability/reports) show the same 4xx signal without SQL.

### Performance

Ask whether queries are slow, blocked, missing indexes, or going to disk.

Poor performance often shows up as long-running sessions, lock waits, sequential scans, bloat, or a cache hit rate below 99%. Confirm with a check, then [Diagnosing](/docs/guides/troubleshooting).

Look for sessions that have been `active` or `idle in transaction` for more than 30 seconds. You can run the same check with [`supabase inspect db long-running-queries`](/docs/reference/cli/supabase-inspect-db-long-running-queries).

```sql
select
  pid,
  usename as role,
  state,
  now() - query_start as duration,
  wait_event_type,
  left(query, 80) as query
from pg_stat_activity
where datname = current_database()
  and pid != pg_backend_pid()
  and state in ('active', 'idle in transaction')
  and now() - query_start > interval '30 seconds'
order by duration desc
limit 20;
```

Also pull [Performance Advisor](/docs/guides/observability/advisors) findings, and use [`supabase inspect db cache-hit`](/docs/reference/cli/supabase-inspect-db-cache-hit) or [`outliers`](/docs/reference/cli/supabase-inspect-db-outliers) for cache and query-time shape. Index or table hit rate below 99% means the instance is reading from disk. [Reports](/docs/guides/observability/reports) and the [Metrics API](/docs/guides/observability/metrics) show CPU, disk IOPS, and connection pressure for the same window. The command catalog and matching SQL live in [Inspect the database](/docs/guides/observability/inspect).

### Usage

Ask whether traffic or storage is growing in a way that will hurt.

Count API requests by path. Compare the count to a recent baseline.

```sql
-- api requests by path
select
  log_attributes['request.path'] as path,
  count() as requests
from logs
where source = 'edge_logs'
group by path
order by requests desc
limit 20;
```

[Reports](/docs/guides/observability/reports) show total requests, disk usage, and database size without SQL. [`supabase inspect db table-sizes`](/docs/reference/cli/supabase-inspect-db-table-sizes) and [`bloat`](/docs/reference/cli/supabase-inspect-db-bloat) name the large relations. The [Management API usage endpoint](/docs/reference/api/v1-get-project-usage-api-count) returns request counts for a script.

Once a check turns up an error message, status, SQLSTATE, or finding, take it to [Diagnosing](/docs/guides/troubleshooting) to confirm the cause, apply a fix, and verify it.
