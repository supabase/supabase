This guide explains how to detect a signal from project data. Confirm one cause before you change anything. Then apply one fix and verify it.

Use this page to:

- Skip to [Diagnosing](/docs/guides/troubleshooting) if you already have a named error
- Run a [Health](#health), [Security](#security), [Performance](#performance), or [Usage](#usage) check if you are observing

## Already have a symptom? [#open-the-directory]

If you already have an error message, HTTP status, SQLSTATE, product error, or a clear advisor finding, skip the checks below. Search [Diagnosing](/docs/guides/troubleshooting). Each article confirms a cause, applies one fix, and verifies it.

## Observing [#notice-a-signal]

If you are checking whether the project is healthy, run a few coarse checks against the data sources in [Observe the data](/docs/guides/monitoring-and-debugging/access-data). You want a count, a rate, or a finding, not a root cause.

- [Logs](/docs/guides/monitoring-and-debugging/advanced-log-filtering) — ClickHouse SQL in the [Logs Explorer](/dashboard/project/_/logs/explorer), MCP `query_logs`, or the [Management API](/docs/reference/api/v1-get-project-logs)
- [Database](/docs/guides/database/inspect) — SQL in the [SQL Editor](/dashboard/project/_/sql), MCP `execute_sql`, or `supabase inspect db`
- [Advisors](/docs/guides/monitoring-and-debugging/advisors) — Studio, MCP `get_advisors`, [`supabase db advisors`](/docs/reference/cli/usage#supabase-db-advisors), or the Management API
- [Metrics](/docs/guides/monitoring-and-debugging/metrics) and [Reports](/docs/guides/monitoring-and-debugging/reports) — Studio charts, or the Metrics API for the same database series

If a check turns up a spike, a named error, or an advisor finding, take that evidence to [Diagnosing](/docs/guides/troubleshooting). If the result is only a count, narrow the time window and pick one identifier (path, status, SQLSTATE, request ID) first.

### Health

Ask whether API error rates or availability are off.

Count API 5xx responses by path. Compare the count to the last quiet window.

```sql
-- api 5xx by path
select
  log_attributes['request.path'] as path,
  count() as errors
from logs
where source = 'edge_logs'
  and toInt32OrZero(log_attributes['response.status_code']) >= 500
group by path
order by errors desc
limit 20;
```

You can also read the same signal on [Reports](/docs/guides/monitoring-and-debugging/reports) (API response errors) without writing SQL. Check connection pressure with [`supabase inspect db role-connections`](/docs/reference/cli/supabase-inspect-db-role-connections), or scrape CPU and connection series from the [Metrics API](/docs/guides/monitoring-and-debugging/metrics).

### Security

Ask whether advisors or authorization failures need review.

Pull [Security Advisor](/docs/guides/monitoring-and-debugging/advisors) findings from Studio, MCP `get_advisors`, the CLI, or the Management API. Then count API 401 and 403 responses by path.

```sql
-- api 401 and 403 by path
select
  log_attributes['request.path'] as path,
  toInt32OrZero(log_attributes['response.status_code']) as status,
  count() as events
from logs
where source = 'edge_logs'
  and toInt32OrZero(log_attributes['response.status_code']) in (401, 403)
group by path, status
order by events desc
limit 20;
```

Read a finding together with the matching log window. Advisors are not a substitute for error rates. Auth error charts in [Reports](/docs/guides/monitoring-and-debugging/reports) show the same 4xx signal without SQL.

### Performance

Ask whether queries are slow, blocked, or missing indexes.

Look for sessions that have been `active` or `idle in transaction` for more than 30 seconds. You can run the same check with [`supabase inspect db long-running-queries`](/docs/reference/cli/supabase-inspect-db-long-running-queries).

```sql
select
  pid,
  usename as role,
  state,
  now() - query_start as duration,
  wait_event_type,
  left(query, 80) as query
from pg_stat_activity
where datname = current_database()
  and pid != pg_backend_pid()
  and state in ('active', 'idle in transaction')
  and now() - query_start > interval '30 seconds'
order by duration desc
limit 20;
```

Also pull [Performance Advisor](/docs/guides/monitoring-and-debugging/advisors) findings, and use [`supabase inspect db cache-hit`](/docs/reference/cli/supabase-inspect-db-cache-hit) or [`outliers`](/docs/reference/cli/supabase-inspect-db-outliers) for cache and query-time shape. [Reports](/docs/guides/monitoring-and-debugging/reports) and the [Metrics API](/docs/guides/monitoring-and-debugging/metrics) show CPU, disk IOPS, and connection pressure for the same window.

### Usage

Ask whether traffic or storage is growing in a way that will hurt.

Count API requests by path. Compare the count to a recent baseline.

```sql
-- api requests by path
select
  log_attributes['request.path'] as path,
  count() as requests
from logs
where source = 'edge_logs'
group by path
order by requests desc
limit 20;
```

[Reports](/docs/guides/monitoring-and-debugging/reports) show total requests, disk usage, and database size without SQL. [`supabase inspect db table-sizes`](/docs/reference/cli/supabase-inspect-db-table-sizes) and [`bloat`](/docs/reference/cli/supabase-inspect-db-bloat) name the large relations. The [Management API usage endpoint](/docs/reference/api/v1-get-project-usage-api-count) returns request counts for a script.

Keep the change only when the original symptom is gone. If verification fails, reverse the change and look again.

<Admonition type="danger">

Deleting data, disabling row-level security, weakening a policy, or terminating a database process can cause data loss or a security incident. Do not let an automated routine perform these changes.

</Admonition>

Escalate to [Support](/dashboard/support/new) when you cannot access the diagnostic source, the evidence points to a platform failure, or a safe fix needs a permission you do not have. Include the project reference, timestamp with time zone, error code, request ID, and sanitized evidence. Do not include passwords, API keys, or personal data.
