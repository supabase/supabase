[Snowflake](https://www.snowflake.com/) is a managed data platform. Supabase Pipelines writes an append-only change history for each replicated Postgres table to Snowflake.

## Prepare Snowflake resources

Create a dedicated Snowflake database, schema, role, and service user for Pipelines. An isolated, otherwise empty schema avoids ownership conflicts with existing objects. Use ordinary unquoted identifiers for the service user and role; Pipelines normalizes the account and user names to uppercase when authenticating.

Run the following as a Snowflake administrator, replacing the clearly fake example names if needed:

```sql
create role if not exists PIPELINES_ROLE;

create user if not exists PIPELINES_USER
  type = service;

grant role PIPELINES_ROLE to user PIPELINES_USER;
alter user PIPELINES_USER set default_role = PIPELINES_ROLE;

create database if not exists PIPELINES_DB;
create schema if not exists PIPELINES_DB.REPLICATED;

grant usage on database PIPELINES_DB to role PIPELINES_ROLE;
grant usage on schema PIPELINES_DB.REPLICATED to role PIPELINES_ROLE;
grant create table on schema PIPELINES_DB.REPLICATED to role PIPELINES_ROLE;
grant create pipe on schema PIPELINES_DB.REPLICATED to role PIPELINES_ROLE;
```

The role that Pipelines uses to create a destination table becomes that table's owner. Pipelines relies on that ownership to alter, truncate, and drop managed tables. `CREATE PIPE` lets Snowflake instantiate the table's managed default Snowpipe Streaming pipe on demand. Don't pre-create destination tables under another role.

Pipelines does not need a virtual warehouse, stage, or manually created pipe object. Snowflake creates a managed default pipe named `<TABLE>-STREAMING` when Pipelines opens a Snowpipe Streaming channel; the role still needs `CREATE PIPE` on the schema for this operation.

Use a separate Snowflake query or transformation role and warehouse for downstream modeling. The pipeline service role doesn't need warehouse, query, or transformation privileges.

### Keep the SQL and streaming roles aligned

Pipelines uses two Snowflake interfaces:

- SQL requests use the optional **Role** configured in the Dashboard, or the user's default role when **Role** is empty.
- Snowpipe Streaming uses the user's `DEFAULT_ROLE`; it does not use the optional **Role** value.

Use one dedicated role for both interfaces. Set it as the service user's `DEFAULT_ROLE`, then leave **Role** empty in the Dashboard or set it to exactly the same role. Otherwise, validation and table creation can succeed through SQL while streaming fails under a different role.

### Generate a key pair

Pipelines authenticates with an RSA key pair. Snowflake requires an RSA key of at least 2048 bits and recommends PKCS #8. Generate either an unencrypted private key:

```bash
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt
```

Or generate an encrypted private key and enter its passphrase when configuring the destination:

```bash
openssl genrsa 2048 | openssl pkcs8 -topk8 -v2 des3 -inform PEM -out rsa_key.p8
```

Derive the public key:

```bash
openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub
```

Register only the public-key body with the service user. Omit the `BEGIN PUBLIC KEY` and `END PUBLIC KEY` lines:

```sql
alter user PIPELINES_USER set rsa_public_key = '<public-key-body>';
```

Keep `rsa_key.p8` and its passphrase secret. Don't commit them, paste them into logs, or send them to support. The Dashboard accepts an unencrypted PKCS #8 or PKCS #1 private key, or an encrypted PKCS #8 private key with its passphrase. Encrypted PKCS #1 keys aren't supported.

See [Snowflake key-pair authentication](https://docs.snowflake.com/en/user-guide/key-pair-auth) to verify the public-key fingerprint and rotate keys with `RSA_PUBLIC_KEY_2`.

### Find the account identifier

Run this query in Snowflake:

```sql
select current_organization_name() || '-' || current_account_name();
```

Enter the result as **Account ID**, for example `MYORG-MYACCOUNT`. Enter the identifier, not a full URL or a dotted locator-and-region hostname. The identifier can contain at most 63 characters. Legacy one-part account locators are also accepted. See [Snowflake account identifiers](https://docs.snowflake.com/en/user-guide/admin-account-identifier) for details.

## Configure Snowflake as a destination

1. Navigate to the [**Database > Replication**](/dashboard/project/_/database/replication) section of the Dashboard.
2. Click **Add destination**.
3. Select **Snowflake**. If it isn't available, [request Early Access](/go/supabase-pipelines-new-destinations).
4. Select a Postgres publication and enter a destination name.
5. Enter the Snowflake settings:
   - **Account ID**: The organization and account identifier, such as `MYORG-MYACCOUNT`.
   - **User**: The dedicated unquoted service user, such as `PIPELINES_USER`.
   - **Database**: The destination database, such as `PIPELINES_DB`.
   - **Schema**: The dedicated destination schema, such as `REPLICATED`.
   - **Role**: Leave empty to use the user's `DEFAULT_ROLE`, or enter that same role exactly.
   - **Private key**: The complete PEM-encoded private key, including its begin and end lines.
   - **Private key passphrase**: Required only for an encrypted PKCS #8 key.
6. Review the [source table requirements](#source-table-requirements) and click **Create and start pipeline**.

Use the exact Snowflake spelling for the database and schema. Unquoted identifiers are normally stored in uppercase. Managed Pipelines run in **AWS `eu-central-1` (Frankfurt)**, so choose a Snowflake account region near Frankfurt when practical.

## How it works

Pipelines uses Snowflake's SQL REST API to validate the database and schema, create and evolve destination tables, apply source truncates, and reset tables. It sends initial-sync and ongoing row data through Snowpipe Streaming. No virtual warehouse is used for these pipeline operations.

Snowflake validation confirms that the configured database and schema are visible. It doesn't prove that the role has `CREATE TABLE` and `CREATE PIPE`, can own managed objects, or can write through Snowpipe Streaming, so keep the permissions and role alignment described above.

### Destination table names

Pipelines flattens each Postgres schema and table name into one Snowflake table name. It doubles existing underscores, joins the names with one underscore, and uppercases the result:

| Postgres table         | Snowflake table          |
| ---------------------- | ------------------------ |
| `public.orders`        | `PUBLIC_ORDERS`          |
| `sales_eu.order_items` | `SALES__EU_ORDER__ITEMS` |

Postgres schema and table names can't start or end with `_`, or contain `"` or `;`. Names that differ only by letter case map to the same Snowflake name. Use ordinary lowercase Postgres names to avoid collisions. Source column names are quoted and preserved, except for the reserved metadata names described below.

### Append-only change history

Each destination table contains the replicated source columns plus two `VARCHAR NOT NULL` metadata columns:

| Column                 | Meaning                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------- |
| `_cdc_operation`       | Lowercase operation: `insert`, `update`, or `delete`.                                                    |
| `_cdc_sequence_number` | Fixed-width hexadecimal commit LSN and transaction ordinal, such as `00000000016b3740/0000000000000002`. |

The metadata names are reserved and can't be used by source columns. Initial-sync rows use `insert` and the shared sequence number `0000000000000000/0000000000000000`.

Snowflake tables are an event history, not a current-state replica:

- An insert appends the new row.
- An update appends the complete new row. It does not append a before image.
- A delete appends either the complete old row with `REPLICA IDENTITY FULL`, or only the identity columns with a primary-key or `USING INDEX` identity. Other source columns are `NULL` in a key-only delete row.
- A source `TRUNCATE` truncates the Snowflake table, resets its streaming state, and does not append a truncate event.

To derive current state, group by a stable source identity, take the latest `_cdc_sequence_number`, then exclude rows whose latest operation is `delete`. The sequence number is an ordering and checkpoint token, not a globally unique event ID. Pipelines has at-least-once delivery semantics, so consumers must tolerate repeated events even though Snowpipe committed offsets suppress ordinary replay.

Table resets drop and recreate the Snowflake table and managed streaming state, erasing its history. Removing a table from the Postgres publication stops new changes after the pipeline restarts but leaves the existing Snowflake table in place.

## Source table requirements

Required `REPLICA IDENTITY` depends on the operations enabled in the Postgres publication:

| Published operations | Required replica identity                                                                                      |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `INSERT` only        | No row identity is required.                                                                                   |
| `DELETE`             | A primary key, `REPLICA IDENTITY USING INDEX`, or `REPLICA IDENTITY FULL`. Identity columns must be published. |
| `UPDATE`             | `REPLICA IDENTITY FULL`.                                                                                       |

Set full replica identity before publishing updates:

```sql
alter table public.your_table replica identity full;
```

Full replica identity increases WAL volume, but lets Pipelines construct the complete new row when Postgres omits unchanged out-of-line TOAST values. A replica identity change affects only new WAL records. If an incompatible update is already retained, reset the affected table after changing the setting.

## Type mapping

Pipelines creates Snowflake columns with these mappings:

| Postgres type                           | Snowflake type                  |
| --------------------------------------- | ------------------------------- |
| `boolean`                               | `BOOLEAN`                       |
| `smallint`, `integer`, `bigint`         | `SMALLINT`, `INTEGER`, `BIGINT` |
| `real`, `double precision`              | `FLOAT`, `DOUBLE`               |
| `date`, `time`                          | `DATE`, `TIME`                  |
| `timestamp`, `timestamp with time zone` | `TIMESTAMP_NTZ`, `TIMESTAMP_TZ` |
| `json`, `jsonb`                         | `VARIANT`                       |
| One-dimensional arrays                  | `ARRAY`                         |
| `oid`                                   | `BIGINT`                        |
| Other types                             | `VARCHAR`                       |

The `VARCHAR` fallback includes character and text types, `numeric`, `time with time zone`, `interval`, `uuid`, `bytea`, bit strings, and custom or unknown types. `bytea` values are lowercase hexadecimal strings. Values retain their serialized representation rather than native Snowflake semantics.

Additional limits apply:

- Multi-dimensional arrays aren't supported. Non-default lower bounds on one-dimensional arrays aren't preserved.
- Floating-point or numeric `NaN` and infinity values are rejected.
- An uncompressed serialized row larger than 2 MiB is rejected.
- Source primary-key, unique, check, length, precision, and nullability constraints aren't copied. Only the two CDC metadata columns are `NOT NULL`.

## Schema change support

Snowflake schema change support is limited during Early Access.

Supported changes:

- Add a column.
- Rename a column.
- Drop a column.

Unsupported or limited changes:

- Changing a column type isn't supported.
- Source table and schema renames aren't supported.
- Nullability changes and changes to defaults on existing columns are ignored.
- Initial table creation can copy compatible literal defaults. A later added column can copy string, numeric, or boolean literal defaults; unsupported defaults are omitted.

Snowflake DDL changes the existing history. Adding a column with a default can populate that value in older rows, renaming a column changes the historical schema, and dropping a column removes it from old events. Snowflake DDL isn't transactional, so an interrupted multi-column change can leave a partially applied schema. Don't alter managed destination objects manually. If a supported change leaves the pipeline failed after restart, [contact support](/dashboard/support/new).

## Troubleshooting

| Symptom                                               | What to check                                                                                                                                                                                                                                              |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication fails                                  | Confirm the account identifier and user, the registered public-key fingerprint, the complete private-key PEM, and the passphrase. Don't provide a passphrase for an unencrypted key.                                                                       |
| Database or schema isn't found                        | Enter its exact Snowflake spelling and confirm the role has `USAGE` on both objects.                                                                                                                                                                       |
| Validation succeeds but table initialization fails    | Confirm the role has `CREATE TABLE` and `CREATE PIPE` on the schema and that no same-name table is owned by another role. The default pipe is system managed; use a dedicated empty schema.                                                                |
| Validation or table creation succeeds but writes fail | Confirm the service user's `DEFAULT_ROLE` is the pipeline role. Leave **Role** empty or set it to that exact role. Also check `CREATE PIPE` and confirm Snowflake network policies allow the account control endpoint and discovered Snowpipe ingest host. |
| Updates or deletes fail                               | Check the publication's operations, replica identity, and included identity columns. Updates require `REPLICA IDENTITY FULL`.                                                                                                                              |
| A row is rejected                                     | Check for multi-dimensional arrays, non-finite numbers, rows over 2 MiB, or source columns named `_cdc_operation` or `_cdc_sequence_number`.                                                                                                               |
| A schema change fails                                 | Check the supported changes above. Because Snowflake DDL can be partially applied, don't repair managed tables manually; [contact support](/dashboard/support/new) with the pipeline ID and error details.                                                 |

Use [pipeline monitoring](/docs/guides/database/replication/pipelines-monitoring) and [replication logs](/dashboard/project/_/logs/replication-logs) to inspect table state, lag, and errors.
