To enable X / Twitter Auth for your project, you need to set up an X OAuth 2.0 application and add the application credentials in the Supabase Dashboard.

## Overview

<Admonition type="caution">

We recommend using the **X / Twitter (OAuth 2.0)** provider. The legacy **Twitter (OAuth 1.0a)**
provider will be deprecated in future releases. If your app already uses the legacy provider, see
[Migrate from Twitter (OAuth 1.0a)](#migrate-from-twitter-oauth-10a) before switching.

</Admonition>

Setting up X / Twitter logins for your application consists of 3 parts:

- Create and configure an X Project and App on the [X Developer Dashboard](https://developer.x.com/en/portal/dashboard).
- Add your X OAuth 2.0 `Client ID` and `Client Secret` to your [Supabase Project](/dashboard).
- Add the login code to your [Supabase JS Client App](https://github.com/supabase/supabase-js).

## Access your X developer account

- Go to [developer.x.com](https://developer.x.com).
- Click on `Sign in` at the top right to log in.

## Create an X OAuth app

- Click `+ Create Project`.
  - Enter your project name, click `Next`.
  - Select your use case, click `Next`.
  - Enter a description for your project, click `Next`.
  - Enter a name for your app, click `Next`.
  - Copy and save your **API Key** and **API Secret Key** (these are used for OAuth 1.0a, which is being deprecated).
  - Click on `App settings` to proceed to next steps.
- At the bottom, you will find `User authentication settings`. Click on `Set up`.
- Under `User authentication settings`, you can configure `App permissions`.
- Make sure you turn ON `Request email from users`.
- Select `Web App...` as the `Type of App`.
- Under `App info` configure the following.
  - Enter your `Callback URL`. Check the **Find your callback URL** section above to learn how to obtain your callback URL.
  - Enter your `Website URL` (tip: try `http://127.0.0.1:port` or `http://www.localhost:port` during development)
  - Enter your `Terms of service URL`.
  - Enter your `Privacy policy URL`.
- Click `Save`.
- After saving, navigate to `Keys and tokens` on your App page.
  - Scroll to the bottom of the page and copy your **Client ID**.
  - Click the `Regenerate` button next to **Client Secret**.
  - In the confirmation modal, click `Yes, regenerate`.
  - Copy and save your **Client Secret**.

## Enter your X credentials into your Supabase project

<$Partial path="social_provider_settings_supabase.mdx" variables={{ "provider": "X / Twitter (OAuth 2.0)" }} />

You can also configure the X / Twitter (OAuth 2.0) auth provider using the Management API:

```bash
# Get your access token from https://supabase.com/dashboard/account/tokens
export SUPABASE_ACCESS_TOKEN="your-access-token"
export PROJECT_REF="your-project-ref"

# Configure X / Twitter (OAuth 2.0) auth provider
curl -X PATCH "https://api.supabase.com/v1/projects/$PROJECT_REF/config/auth" \
  -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "external_x_enabled": true,
    "external_x_client_id": "your-x-client-id",
    "external_x_secret": "your-x-client-secret"
  }'
```

## Migrate from Twitter (OAuth 1.0a) [#migrate-from-twitter-oauth-10a]

Supabase Auth treats the legacy `twitter` provider and the `x` provider as separate providers. When an existing `twitter` user signs in with `x` for the first time, the new `x` identity is attached to their account only through [automatic linking](/docs/guides/auth/auth-identity-linking#automatic-linking), which matches identities by email address. The X user ID isn't compared.

<Admonition type="caution">

If a user changed the email address on their X account after signing up with `twitter`, the emails no longer match. Their first `x` sign-in creates a new, separate user, or links the `x` identity to a different existing user that already has the new email address. Later sign-ins use the `x` identity, so the user keeps landing in the wrong account.

</Admonition>

To migrate existing users without creating duplicates:

1. Keep both the **Twitter (OAuth 1.0a)** and **X / Twitter (OAuth 2.0)** providers enabled during the migration.
2. Enable [manual linking](/docs/guides/auth/auth-identity-linking#manual-linking-beta) for your project.
3. While a user is still signed in with their `twitter` identity, link their `x` identity to the same account. Manual linking doesn't require the email addresses to match. After the user returns from X, check that they authorized the same X account. The `id` of each identity is the X user ID, so both identities must have the same `id`:

   ```js
   import { createClient } from '@supabase/supabase-js'

   const supabase = createClient('https://your-project-id.supabase.co', 'sb_publishable_...')

   // ---cut---
   async function linkXIdentity() {
     const { data, error } = await supabase.auth.getUserIdentities()
     if (error) throw error

     const twitterIdentity = data.identities.find((identity) => identity.provider === 'twitter')
     const xIdentity = data.identities.find((identity) => identity.provider === 'x')

     if (!xIdentity) {
       // Redirects the user to X. Call linkXIdentity() again after they return.
       const { error: linkError } = await supabase.auth.linkIdentity({ provider: 'x' })
       if (linkError) throw linkError
       return
     }

     if (twitterIdentity && xIdentity.id !== twitterIdentity.id) {
       throw new Error('The linked X account does not match the original Twitter account.')
     }
   }
   ```

4. Switch your sign-in code to `provider: 'x'` once most active users have linked their `x` identity. Keep a way to sign in with `twitter` for users who haven't linked yet, so they can complete step 3 instead of creating a new user.

To check for users that were already affected, find `twitter` and `x` identities that share a `provider_id` but belong to different users. Run this query again after you switch sign-in to `x`:

```sql
select
  twitter.provider_id,
  twitter.user_id as twitter_user_id,
  x.user_id as x_user_id
from
  auth.identities as twitter
  join auth.identities as x on x.provider_id = twitter.provider_id and x.provider = 'x'
where twitter.provider = 'twitter' and x.user_id != twitter.user_id;
```

How you resolve each pair depends on your application data. The user that holds the `x` identity might be an account the person created separately with the same email, so confirm before you merge or delete anything. Before you delete a user, check its other identities and MFA factors so the person doesn't lose a way to sign in. For example, you can move any data created by the duplicate user to the original user, delete the duplicate user, and have the user link their `x` identity again from the original account.
