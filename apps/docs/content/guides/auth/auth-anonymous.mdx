[Enable anonymous sign-ins](/dashboard/project/_/auth/providers) to give users an authenticated experience without asking for an email address, password, OAuth provider, or other personally identifiable information (PII). Later, the user can link an authentication method and become a permanent user. On a self-hosted or local project, enable it in the [CLI configuration](/docs/guides/local-development/cli/config) instead.

Use anonymous sign-ins to build:

- E-commerce applications, such as shopping carts before checkout
- Full-feature demos without collecting personal information
- Temporary or throwaway accounts

## How anonymous users differ

An anonymous user behaves like a permanent user, but loses access to their account when they sign out, clear browsing data, or use another device. Don't confuse an anonymous user with the `anon` API key, which doesn't create a user at all.

|                                   | Anonymous user                  | Permanent user  | `anon` API key |
| --------------------------------- | ------------------------------- | --------------- | -------------- |
| Creates a user                    | Yes, with `signInAnonymously()` | Yes             | No             |
| Postgres role                     | `authenticated`                 | `authenticated` | `anon`         |
| `is_anonymous` claim              | `true`                          | `false`         | None           |
| Survives sign-out or a new device | No                              | Yes             | Not applicable |

<Admonition type="caution">

Review your existing RLS policies before enabling anonymous sign-ins. Anonymous users use the `authenticated` role, so any policy written for signed-in users also applies to them. To tell anonymous users apart from permanent users, see [Access control](#access-control).

</Admonition>

## Access control

An anonymous user uses the `authenticated` role, like a permanent user. To tell them apart in row-level security (RLS) policies, check the `is_anonymous` claim in the JWT that `auth.jwt()` returns.

Run the following SQL using the [SQL Editor](/dashboard/project/_/sql) in the Supabase Dashboard or with `psql` over a direct connection. To connect with `psql`, see [Direct connection](/docs/guides/database/connecting-to-postgres#direct-connection).

```sql
create policy "Only permanent users can post to the news feed"
on news_feed as restrictive for insert
to authenticated
with check ((select (auth.jwt()->>'is_anonymous')::boolean) is false );

create policy "Permanent users can post to the news feed"
on news_feed for insert
to authenticated
with check ( true );

create policy "Anonymous and permanent users can view the news feed"
on news_feed for select
to authenticated
using ( true );
```

<Admonition type="caution" title="Linked users stay anonymous until the token refreshes">

If your policies check the `is_anonymous` claim, a guest who links an email, phone, or OAuth identity is still treated as anonymous until their session refreshes, which can take up to the JWT expiry time. Until then, their requests fail with error `42501`. Avoid this by either:

- [Refreshing the session after linking](#refresh-the-session-after-linking)
- Checking `is_anonymous` in `auth.users` instead of the claim, as shown below

</Admonition>

To check the current state, read `is_anonymous` from `auth.users` through a [`security definer` function](/docs/guides/database/postgres/row-level-security#use-security-definer-functions). Create the function in a schema the Data API doesn't expose, such as `private`, and set `search_path = ''`.

Run the following SQL using the [SQL Editor](/dashboard/project/_/sql) in the Supabase Dashboard or with `psql` over a direct connection. To connect with `psql`, see [Direct connection](/docs/guides/database/connecting-to-postgres#direct-connection).

```sql
create schema if not exists private;

create function private.is_permanent_user()
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1 from auth.users
    where id = (select auth.uid()) and is_anonymous is false
  );
$$;

revoke all on function private.is_permanent_user() from public;
grant usage on schema private to authenticated;
grant execute on function private.is_permanent_user() to authenticated;

alter policy "Only permanent users can post to the news feed"
on news_feed
with check ( (select private.is_permanent_user()) );
```

The `alter policy` statement replaces the claim check in the policy from the previous example, so stale tokens no longer fail. For a fresh setup, create the policy with `create policy ... as restrictive for insert` and the same `with check` expression, and add the permissive insert policy from the previous example.

<Admonition type="note" title="Use restrictive policies">

RLS policies are permissive by default, and Postgres combines permissive policies with `OR`. Make the anonymous-user check a restrictive policy so other policies can't bypass it.

A restrictive policy on its own allows nothing. Pair it with at least one permissive policy for the same operation that returns true.

</Admonition>

## Convert an anonymous user to a permanent user

Converting an anonymous user to a permanent user requires [linking an identity](/docs/guides/auth/auth-identity-linking#manual-linking-beta) to the user. This requires you to [enable manual linking](/dashboard/project/_/auth/providers) in your Supabase project.

Use [`updateUser()`](/docs/reference/javascript/auth-updateuser) to link an email or phone identity to the anonymous user. The user must verify their email address or phone number before you can add a password.

```js
import { createClient } from '@supabase/supabase-js'

const supabase = createClient('https://your-project-id.supabase.co', 'sb_publishable_...')

// ---cut---
const { data: updateEmailData, error: updateEmailError } = await supabase.auth.updateUser({
  email: 'valid.email@supabase.io',
})

// verify the user's email by clicking on the email change link
// or entering the 6-digit OTP sent to the email address

// once the user has been verified, update the password
const { data: updatePasswordData, error: updatePasswordError } = await supabase.auth.updateUser({
  password: 'password',
})
```

### Refresh the session after linking

Linking an identity makes the user permanent at once, but the access token the client holds still has `is_anonymous: true` until the session refreshes. RLS policies that check the claim keep treating the user as anonymous until then. Refresh the session after linking so the next request carries the updated claim:

```js
import { createClient } from '@supabase/supabase-js'

const supabase = createClient('https://your-project-id.supabase.co', 'sb_publishable_...')

// ---cut---
const { data, error } = await supabase.auth.refreshSession()
```

To write policies that don't depend on the token, see [Access control](#access-control).

### Resolve identity conflicts

Data conflicts can arise when an anonymous user becomes a permanent user. For example, an e-commerce app might let an anonymous user add items to a cart without signing up or signing in. When that user signs in to an existing account, decide how to resolve conflicts in the cart:

1. Overwrite the items in the cart with those in the existing account
2. Overwrite the items in the cart with those from the anonymous user
3. Merge the items in the cart together

#### Link an anonymous user to an existing account

To link an anonymous user to an existing account instead of creating a new permanent account, handle the conflicts yourself. A general approach:

```javascript
// 1. Get the current session and verify the user is anonymous
const { data: anonData, error: anonError } = await supabase.auth.getSession()

if (!anonData.session?.user?.is_anonymous) {
  throw new Error('User is not anonymous. This flow only applies to anonymous users.')
}

// 2. Attempt to update the user with the existing email
const { data: updateData, error: updateError } = await supabase.auth.updateUser({
  email: 'valid.email@supabase.io',
})

// 3. Handle the error (since the email belongs to an existing user)
if (updateError) {
  console.log('This email belongs to an existing user. Please sign in to that account.')

  // 4. Sign in to the existing account
  const {
    data: { user: existingUser },
    error: signInError,
  } = await supabase.auth.signInWithPassword({
    email: 'valid.email@supabase.io',
    password: 'user_password',
  })

  if (existingUser) {
    // 5. Reassign entities tied to the anonymous user
    // This step will vary based on your specific use case and data model
    const { data: reassignData, error: reassignError } = await supabase
      .from('your_table')
      .update({ user_id: existingUser.id })
      .eq('user_id', anonData.session.user.id)

    // 6. Implement your chosen conflict resolution strategy
    // This could involve merging data, overwriting, or other custom logic
    await resolveDataConflicts(anonData.session.user.id, existingUser.id)
  }
}

// Helper function to resolve data conflicts (implement based on your strategy)
async function resolveDataConflicts(anonymousUserId, existingUserId) {
  // Implement your conflict resolution logic here
  // This could involve ignoring the anonymous user's metadata, overwriting the existing user's metadata, or merging the data of both the anonymous and existing user.
}
```

## Abuse prevention and rate limits

Because anonymous users are stored in your database, bad actors can abuse the endpoint to inflate your [database size](/docs/guides/platform/database-size). [Enable invisible CAPTCHA or Cloudflare Turnstile](/docs/guides/auth/auth-captcha) to prevent abuse of anonymous sign-ins. Anonymous sign-ins have an IP-based rate limit of 30 requests per hour, which you can change in the [dashboard](/dashboard/project/_/auth/rate-limits). For every rate limit, see [Rate limiting, resource allocation, and abuse prevention](/docs/guides/deployment/going-into-prod#rate-limiting-resource-allocation--abuse-prevention).

## Clean up anonymous users

Supabase doesn't delete anonymous users automatically. To delete them, run SQL like this:

```sql
-- deletes anonymous users created more than 30 days ago
delete from auth.users
where is_anonymous is true and created_at < now() - interval '30 days';
```
