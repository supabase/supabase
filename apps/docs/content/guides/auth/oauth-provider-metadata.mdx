When a user signs in with a social or OAuth provider, Supabase Auth copies the profile information returned by the provider into the user's metadata. The same data is stored in the `identity_data` of the matching [identity](/docs/guides/auth/identities).

You can read it in these places:

- `user.user_metadata` in the client libraries, which maps to the `raw_user_meta_data` column of `auth.users`.
- `identity_data` on each entry of `user.identities`, which maps to the `identity_data` column of `auth.identities`.

<Admonition type="caution">

`user_metadata` can be edited by the signed-in user, so don't use it in authorization logic or RLS policies. Use `app_metadata` or your own tables for that.

</Admonition>

Which fields are present depends on the provider and on the scopes and permissions you request. Fields that the provider doesn't return are left out, except `email_verified` and `phone_verified`, which are always present. Provider APIs change, so treat this page as a reference for what Supabase Auth maps, not as a guarantee of what each provider returns.

## Common fields

Every OAuth sign-in stores these fields:

| Field            | Type      | Description                                                                                              |
| ---------------- | --------- | -------------------------------------------------------------------------------------------------------- |
| `iss`            | `string`  | The issuer or API host of the provider.                                                                  |
| `sub`            | `string`  | The user's unique ID at the provider.                                                                    |
| `provider_id`    | `string`  | The user's unique ID at the provider. Same value as `sub`.                                               |
| `email`          | `string`  | The email that Auth selected: the one the provider marks as primary, otherwise the last one it returned. |
| `email_verified` | `boolean` | Whether the provider reports the email as verified.                                                      |
| `phone_verified` | `boolean` | `false` for built-in providers.                                                                          |

Most providers also fill in some of the following fields. The last four are older fields that Supabase Auth keeps for backwards compatibility. Prefer `name`, `picture` and `preferred_username` in new code.

| Field                | Type     | Description                                                     |
| -------------------- | -------- | --------------------------------------------------------------- |
| `name`               | `string` | The user's display name.                                        |
| `picture`            | `string` | URL of the user's avatar.                                       |
| `preferred_username` | `string` | The user's handle or username.                                  |
| `nickname`           | `string` | An alternate display name.                                      |
| `avatar_url`         | `string` | Same as `picture`. Kept for backwards compatibility.            |
| `full_name`          | `string` | Same as `name`. Kept for backwards compatibility.               |
| `user_name`          | `string` | Same as `preferred_username`. Kept for backwards compatibility. |
| `slug`               | `string` | Handle on some providers. Kept for backwards compatibility.     |

Provider-specific values that don't fit these fields are stored in a nested `custom_claims` object.

## Example

A GitHub sign-in produces `user_metadata` like this:

```json
{
  "iss": "https://api.github.com",
  "sub": "1234567",
  "provider_id": "1234567",
  "name": "Jane Doe",
  "preferred_username": "janedoe",
  "user_name": "janedoe",
  "full_name": "Jane Doe",
  "avatar_url": "https://avatars.githubusercontent.com/u/1234567?v=4",
  "email": "jane@example.com",
  "email_verified": true,
  "phone_verified": false
}
```

## Updating metadata on later sign-ins

Each time a user signs in with a provider, Supabase Auth merges the provider's values into `user_metadata`. Fields that you added yourself with `updateUser({ data: { ... } })` are kept unless the provider returns a field with the same name, in which case the provider value overwrites yours. Store values you want to control under keys that providers don't use. `custom_claims` is one key, so it is replaced as a whole. Fields that a provider stops returning stay in `user_metadata`.

`identity_data` is replaced with the provider's latest values on each sign-in. For example, the Apple name that Apple sends only on the first sign-in stays in `user_metadata` but is gone from `identity_data` after the next sign-in.

## Custom OAuth and OIDC providers

For [custom OAuth providers](/docs/guides/auth/custom-oauth-providers), claims that you list in the provider's custom claims allowlist are copied into `custom_claims`.
