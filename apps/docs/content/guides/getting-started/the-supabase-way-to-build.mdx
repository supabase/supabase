Supabase is more than hosted Postgres. It's a set of composable building blocks you grow into. The Supabase way is to start with the database, add a building block only when a real need appears, and keep as much logic as possible in Postgres.

The [Architecture](/docs/guides/getting-started/architecture) page tells you what the pieces are. This page tells you which to reach for, and when. Each stage below names the need that triggers it, the block you add, the mental model to hold, and a common mistake to avoid. Follow the links to build each piece.

## The progression at a glance

| Your app needs to…                  | Reach for                                                    | Keep in mind                                                        |
| ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------- |
| Store and query data, expose an API | [Postgres + auto APIs](#start-with-your-database)            | Your schema is your API                                             |
| Know who is calling                 | [Auth](#add-users-auth)                                      | Auth issues an identity the database can read                       |
| Show each user only their own data  | [Row Level Security](#add-authorization-in-the-database-rls) | Authorization is data, enforced by Postgres                         |
| Reflect changes without a refresh   | [Realtime](#add-live-updates-realtime)                       | Subscribe to the database, don't poll it                            |
| Handle uploads and files            | [Storage](#add-files-storage)                                | Files obey the same access rules as your rows                       |
| Run server-side logic and secrets   | [Edge Functions](#add-server-side-logic-edge-functions)      | Data-shaped logic in Postgres, integration-shaped logic at the edge |
| Serve real traffic safely           | [Harden for production](#harden-for-production)              | Verify, pool, observe, back up                                      |

You don't need all of it. Most apps start at the first row and stop wherever their needs stop. Add the next block when a concrete need shows up, not before.

## Start with your database

Every Supabase project is a full Postgres database, and Supabase generates a [REST API](/docs/guides/api) and a [GraphQL API](/docs/guides/graphql/api) from your schema automatically. Design your tables well and you have a working backend with no server code.

**Mental model:** your schema is your API. The shape of your data is the shape of what clients can do.

**Enough on its own for:** internal tools, prototypes, read-heavy apps, and anything single-user or trusted-client.

Avoid hand-writing a REST server that only forwards create, read, update, and delete calls to the database. That rebuilds what PostgREST already generates for you. Put your effort into the schema instead.

## Add users: Auth

When your app needs to know who is making a request, add [Supabase Auth](/docs/guides/auth). It manages users and issues a signed JWT that carries the caller's identity.

**Mental model:** auth issues a verifiable identity (a JWT) that the database itself can read. It's the key that unlocks per-user behavior everywhere else.

**Trigger:** any multi-user app, personalization, or anything that must be private to an account.

## Add authorization in the database: RLS

This is the pivotal Supabase way moment. Once you have users, each user needs to see only their own data. With [Row Level Security](/docs/guides/database/postgres/row-level-security) (RLS), you write that rule once, as a policy on the table, and Postgres enforces it on every query, from every client.

**Mental model:** authorization is data, enforced by Postgres, not logic scattered across your app. The policy lives next to the rows it protects.

**Trigger:** users must not see each other's rows, multi-tenant apps, and anything where a leaked query would leak data.

<Admonition type="caution" title="Don't filter by user in application code">

App-layer filtering leaks data the moment one query forgets the filter, a new client is added, or someone writes a new endpoint. A query like `select * from orders where user_id = $currentUser` looks safe, but it can be bypassed, gets duplicated, and drifts out of sync. An RLS policy can't be forgotten, because the database applies it to every request.

</Admonition>

## Add live updates: Realtime

When your UI has to reflect changes as they happen, [Realtime](/docs/guides/realtime) streams database changes, broadcasts messages, and tracks presence over WebSockets.

**Mental model:** subscribe to the database instead of polling it. The client reacts to change; it doesn't ask "anything new?" on a timer.

**Trigger:** dashboards that update live, chat, collaboration, presence indicators, and multiplayer.

Avoid polling loops. A `setInterval` that re-fetches every few seconds wastes requests, adds latency, and still misses fast changes. Subscribe once and let the change come to you.

## Add files: Storage

For uploads, images, and documents, [Storage](/docs/guides/storage) gives you S3-compatible object storage that keeps its metadata in Postgres, so the same access rules that guard your rows also guard your files.

**Mental model:** files are governed by the same authorization model as your data. Access to an object is a policy, not a separate access-control system to keep in sync.

**Trigger:** user avatars, attachments, media, and any binary a user owns.

Keep object access on the same RLS foundation as your data. File rules that live in a separate system, disconnected from your users table, drift out of sync with your data rules.

## Add server-side logic: Edge Functions

Some logic can't live in the client, because it needs secrets, and isn't a good fit for the database, because it calls third-party APIs or reacts to events. That's what [Edge Functions](/docs/guides/functions) are for: TypeScript running close to your users.

**Mental model:** put data-shaped logic in Postgres (triggers, [database functions](/docs/guides/database/functions), and RPC) and integration-shaped logic at the edge (webhooks, third-party calls, and anything holding a secret key). For logic that's really about your data, prefer a Postgres function, closer to the data and easier to secure.

**Trigger:** payment webhooks, calls to an external API, sending email, and any code that must hold a credential the browser can't see.

<Admonition type="danger" title="Never ship a secret key in client code">

A secret key in frontend code is exposed to anyone who opens the browser. Keep credentials in an Edge Function or a database function, where the client can't read them.

</Admonition>

## Harden for production

Before real traffic, confirm the app is secure and ready to scale. Run the [advisors](/docs/guides/observability/advisors), review every RLS policy, pool connections with [Supavisor](/docs/guides/database/connecting-to-postgres), set up observability and backups, and check query and index performance.

**Mental model:** production readiness is verification, not new features. The blocks are already in place; now you confirm they hold.

**Trigger:** launch, real users, real data, and real money.
