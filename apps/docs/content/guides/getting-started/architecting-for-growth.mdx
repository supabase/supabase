Supabase is more than hosted Postgres. It's a set of composable building blocks you grow into. The Supabase way is this: **start with the database, add a building block only when a real need appears, and keep as much logic as possible in Postgres.**

The [Architecture](/docs/guides/getting-started/architecture) page tells you what the pieces are. This page tells you which to reach for, and when. Each stage below names the need that triggers it, the block you add, the mental model to hold, and the anti-pattern it prevents. Follow the links to build each piece.

## The progression at a glance

| Your app needs to…                  | Reach for                                                    | Keep in mind                                                        |
| ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------- |
| Store and query data, expose an API | [Postgres + auto APIs](#start-with-your-database)            | Your schema is your API                                             |
| Know who is calling                 | [Auth](#add-users-auth)                                      | Auth issues an identity the database can read                       |
| Show each user only their own data  | [Row Level Security](#add-authorization-in-the-database-rls) | Authorization is data, enforced by Postgres                         |
| Reflect changes without a refresh   | [Realtime](#add-live-updates-realtime)                       | Subscribe to the database, don't poll it                            |
| Handle uploads and files            | [Storage](#add-files-storage)                                | Files obey the same RLS model as your rows                          |
| Run server-side logic and secrets   | [Edge Functions](#add-server-side-logic-edge-functions)      | Data-shaped logic in Postgres, integration-shaped logic at the edge |
| Serve real traffic safely           | [Harden for production](#harden-for-production)              | Verify, pool, observe, back up                                      |

You don't need all of it. Most apps start at the first row and stop wherever their needs stop. Add the next block when a concrete need shows up, not before.

## Start with your database

Every Supabase project is a full Postgres database, and Supabase generates a [REST API](/docs/guides/api) and a [GraphQL API](/docs/guides/graphql/api) from your schema automatically. Design your tables well and you have a working backend with no server code.

**Mental model:** your schema is your API. The shape of your data is the shape of what clients can do.

**Enough on its own for:** internal tools, prototypes, read-heavy apps, anything single-user or trusted-client.

<Admonition type="note" title="Anti-pattern: hand-writing a CRUD server">

If you find yourself building a REST server that only forwards create, read, update, and delete calls to the database, you're rebuilding what PostgREST already generates. Let the database expose the API and put your effort into the schema.

</Admonition>

**Build it:** [Database overview](/docs/guides/database/overview) · [REST API](/docs/guides/api) · [Connect a framework](/docs/guides/getting-started/quickstarts/nextjs)

## Add users: Auth

The moment your app needs to know who is making a request, add [Supabase Auth](/docs/guides/auth). It manages users and issues a signed JWT that carries the caller's identity.

**Mental model:** auth issues a verifiable identity (a JWT) that the database itself can read. Sign-in isn't a separate silo. It's the key that unlocks per-user behavior everywhere else.

**Trigger:** any multi-user app, personalization, or anything that must be private to an account.

**Build it:** [Auth overview](/docs/guides/auth) · [Server-side auth](/docs/guides/auth/server-side) · [Social login](/docs/guides/auth/social-login)

## Add authorization in the database: RLS

This is the pivotal Supabase way moment. Once you have users, you need each user to see only their own data. With [Row Level Security](/docs/guides/database/postgres/row-level-security), you write that rule once, as a policy on the table, and Postgres enforces it on every query, from every client, forever.

**Mental model:** authorization is data, enforced by Postgres, not logic scattered across your app. The policy lives next to the rows it protects.

**Trigger:** users must not see each other's rows; multi-tenant apps; anything where a leaked query would leak data.

<Admonition type="caution" title="Anti-pattern: filtering by user in application code">

`select * from orders where user_id = $currentUser` in your app looks fine until one query forgets the filter, a second client is added, or a new developer writes a new endpoint. App-layer filtering can be bypassed, gets duplicated, and drifts out of sync. An RLS policy can't be forgotten, because the database applies it to every request.

</Admonition>

**Build it:** [Row Level Security](/docs/guides/database/postgres/row-level-security) · [Column Level Security](/docs/guides/database/postgres/column-level-security)

## Add live updates: Realtime

When your UI has to reflect changes as they happen, [Realtime](/docs/guides/realtime) streams database changes, broadcasts messages, and tracks presence over WebSockets.

**Mental model:** subscribe to the database instead of polling it. The client reacts to change; it doesn't ask "anything new?" on a timer.

**Trigger:** dashboards that update live, chat, collaboration, presence indicators, multiplayer.

<Admonition type="note" title="Anti-pattern: polling loops">

A `setInterval` that re-fetches every few seconds wastes requests, adds latency, and still misses fast changes. Subscribe once and let the change come to you.

</Admonition>

**Build it:** [Realtime overview](/docs/guides/realtime) · [Postgres Changes](/docs/guides/realtime/postgres-changes) · [Presence](/docs/guides/realtime/presence)

## Add files: Storage

For uploads, images, and documents, [Storage](/docs/guides/storage) gives you S3-compatible object storage that keeps its metadata in Postgres, so the same RLS model that guards your rows also guards your files.

**Mental model:** files are governed by the same authorization model as your data. Access to an object is a policy, not a separate ACL system to keep in sync.

**Trigger:** user avatars, attachments, media, any binary a user owns.

<Admonition type="note" title="Anti-pattern: bucket permissions disconnected from your auth">

If file access rules live in a separate ACL that doesn't know about your users table, they will drift from your data rules. Keep object access on the same RLS foundation as everything else.

</Admonition>

**Build it:** [Storage overview](/docs/guides/storage) · [Access control](/docs/guides/storage/security/access-control) · [Image transformations](/docs/guides/storage/serving/image-transformations)

## Add server-side logic: Edge Functions

Some logic can't live in the client (it needs secrets) and isn't a good fit for the database (it calls third-party APIs or reacts to events). That's [Edge Functions](/docs/guides/functions): TypeScript running close to your users.

**Mental model:** put data-shaped logic in Postgres (triggers, [database functions](/docs/guides/database/functions), RPC) and integration-shaped logic at the edge (webhooks, third-party calls, anything holding a secret key).

**Trigger:** payment webhooks, calling an external API, sending email, any code that must hold a credential the browser can't see.

<Admonition type="caution" title="Anti-pattern: leaking secrets to the client, or overusing the edge">

A secret key in frontend code is a secret no longer. Move that call to an Edge Function. Equally, don't reach for the edge to do what a Postgres function does better and closer to the data. Match the tool to the shape of the work.

</Admonition>

**Build it:** [Edge Functions overview](/docs/guides/functions) · [Database functions](/docs/guides/database/functions) · [Database webhooks](/docs/guides/database/webhooks)

## Harden for production

Before real traffic, close the gap between "it works" and "it's safe at scale." Run the [advisors](/docs/guides/observability/advisors), review every RLS policy, pool connections with [Supavisor](/docs/guides/database/connecting-to-postgres), set up observability and backups, and check query and index performance.

**Mental model:** production readiness is verification, not new features. The blocks are already in place; now you confirm they hold.

**Trigger:** launch, real users, real data, real money.

**Build it:** [Production checklist](/docs/guides/deployment/going-into-prod) · [Security](/docs/guides/security/product-security) · [Performance and advisors](/docs/guides/observability/advisors)
