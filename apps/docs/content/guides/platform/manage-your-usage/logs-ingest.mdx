## What you are charged for

You are charged for the total volume of log data that Supabase ingests across all your project's services (Postgres, API gateway, Auth, Storage, Realtime, Edge Functions, and others) during the billing cycle, measured in GB.

## How charges are calculated

Logs Ingest is charged per GB of log data ingested during the billing cycle.

### Usage on your invoice

Usage is shown as "Logs Ingest" on your invoice.

## View usage

You can view Logs Ingest usage on the [organization's usage page](/dashboard/org/_/usage) of the Dashboard. The page shows the usage of all projects by default. To view the usage for a specific project, select it from the dropdown. You can also select a different time period.

## Optimize usage

Every service in your Supabase project generates logs automatically — you don't write them directly. Log volume scales with your application's traffic and behavior. Your project's database (Postgres) can also be configured to record different kinds of activity, such as every query it runs, every time an app connects, and how long things take. Each recorded event is a "log line," and log lines are what count toward your ingest usage.

Most projects don't need to log everything, all the time. Turning off a log type means you won't have that information if something goes wrong later, for example a slow query, a security incident, or a connection storm. If your team relies on these logs for debugging, security audits, or compliance requirements, check with them before you change a setting. When in doubt, reduce the volume of a log type rather than turning it off completely — for example, raise a threshold rather than disabling logging outright.

You change all of the Postgres settings below through [Custom Postgres Configuration](/docs/guides/database/custom-postgres-config), either from the SQL Editor or the Supabase CLI. Some changes take effect immediately; others require a database restart. The CLI has a `--no-restart` option if you want to batch several changes together before restarting.

### Start with the two biggest levers

If you only change two things, change these first — they're responsible for most log volume on most projects.

- **`log_statement`.** When set to `all` or `mod`, Postgres writes out the actual text of every query your application runs. On an active project, this produces high log volume in a short time, since it logs once per query rather than once per problem. Set it to `none` if you don't manually read through raw query logs to debug your application, for example if your team relies on an AI coding assistant, an APM tool, or the Query Performance dashboard instead. Keep it on if you routinely read query text in the Logs Explorer to debug issues, or you have a compliance requirement to retain a full statement audit trail.
- **`log_min_duration_statement`.** Logs the duration, and optionally the text, of any query that takes longer than a threshold you set, in milliseconds. A threshold of `0` logs every query's duration and generates volume similar to `log_statement`. Raise the threshold (for example, from a few milliseconds to 1-2 seconds) if you only care about queries that are slow enough to notice. Keep it low only while you're actively in a performance-tuning phase, and raise it back up once that investigation is done.

### Check these often-overlooked settings

- **`log_connections` and `log_disconnections`.** Writes a log line every time a client connects to your database, and another when it disconnects. This is usually low-volume for an app with a handful of long-lived connections, but if your application opens and closes a new connection for every request instead of reusing a pooled connection, it can generate two log lines per request. Turn it off if you don't need a record of exactly when every connection opened and closed. Keep it on if you're troubleshooting connection exhaustion or connection spikes, or have a security requirement to log all connection activity. If this setting is generating a lot of volume, your app may not be using a connection pooler such as Supavisor, which Supabase provides by default — connecting through the pooler reduces both log volume and the risk of running out of connections.
- **`log_autovacuum_min_duration`.** Logs when Postgres's autovacuum maintenance process runs and how long it took. On a database with many frequently updated tables, a low threshold can produce a steady trickle of log lines over a month. Raise the threshold, or turn it off, if you're not actively diagnosing a table-maintenance problem. Keep it on with a reasonable threshold if you've had autovacuum-related performance issues before.
- **`log_temp_files`.** Logs when a query needs more working memory than it's been given and has to write temporary data to disk — usually a sign of a large sort or join. Turn it off if you're not actively tuning query performance around memory usage. Keep it on if you're investigating slow queries related to sorting or joining large amounts of data.
- **`log_lock_waits`.** Logs when a query waits an unusually long time to acquire a lock. This is normally low-volume unless your application has real lock contention. Turn it off if you're not seeing symptoms of queries hanging. Keep it on if multiple processes write to the same data concurrently and you've seen unexplained slowdowns before.

### Check this if your logs seem unusually large for no clear reason

**`log_min_messages`** controls the verbosity of Postgres's own internal logging, separate from query activity. If this was turned up to a debug level while troubleshooting a specific issue and never turned back down, it can produce a large, ongoing volume of internal messages that aren't useful for day-to-day monitoring. Turn it back down if you're not actively working with Supabase support or a database specialist on a deep internal Postgres issue right now. This is one of the most common causes of an unexpected, sustained jump in log volume.

### Settings you can generally leave alone

`log_checkpoints`, `log_replication_commands`, `log_recovery_conflict_waits`, and `log_startup_progress_interval` are either low-volume by nature or only relevant if you use specific features such as replication. Unless you know you're using the related feature, these rarely contribute meaningfully to your total ingest.

After you change a setting, give it a day or two, then check your ingest usage trend in the Dashboard, or your log volume in the Logs Explorer, to confirm the change had the effect you expected. Volume can be uneven day-to-day depending on traffic, so look at the trend over several days before drawing conclusions. If you're not sure which setting is responsible for your current usage, check which kind of log entries make up most of your volume in the Logs Explorer before changing anything.
