## Symptoms

An Auth request returns HTTP `500`, and the Auth logs contain `Database error querying schema`. This message is a wrapper around a more specific database error; it does not prove that every nullable value in `auth.users` is invalid.

## Confirm the cause

1. Reproduce the failing Auth operation and record its timestamp.
2. Inspect the [Auth logs](/dashboard/project/_/logs/auth-logs) and [Postgres logs](/dashboard/project/_/logs/postgres-logs) over the same time window.
3. Identify the exact column, constraint, trigger, function, and SQLSTATE reported by the database.
4. Review any SQL, ORM migration, import, or trigger that writes directly to the `auth` schema.

## Resolve

Revert the project-owned schema change or data write identified by the logs. Do not run a blanket update that converts every `NULL` in an Auth column to an empty string: some Auth fields are legitimately nullable, and broad updates can create invalid or duplicate identity data.

If the log identifies a known token column that must contain an empty string, follow the article for that exact error, such as [confirmation_token converting NULL to string](/docs/guides/troubleshooting/scan-error-on-column-confirmation_token-converting-null-to-string-is-unsupported-during-auth-login-a0c686). Otherwise, use [Resolving 500 status authentication errors](/docs/guides/troubleshooting/resolving-500-status-authentication-errors-7bU5U8) to match the database evidence to a trigger, constraint, ownership, or service-schema problem.

## Verify

Repeat the original Auth operation and confirm that it succeeds. Check the Auth and Postgres logs over the new time window and verify that the same database error no longer appears.

## Escalate

Open a [support ticket](/dashboard/support/new) if the failing object is owned by Supabase, the exact database error is not visible, or repairing project-owned changes would require guessing at service-managed Auth data. Include the project reference, timestamp, operation, SQLSTATE, and sanitized log messages.
