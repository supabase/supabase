Use this article to trace a failed Database API request from the edge to Postgres.

## Symptoms

The Database API returns a `4xx` or `5xx` response, but the client error does not identify whether the request was rejected by the edge network, PostgREST, or Postgres.

## Confirm the cause

1. Record the failed request's timestamp with time zone, HTTP method, path, status code, and request ID when one is available.
2. Open the [Logs Explorer](/dashboard/project/_/logs/explorer), select a narrow time range around the request, and query API errors:

   ```sql
   select
     timestamp,
     log_attributes['request.method'] as method,
     log_attributes['request.path'] as path,
     toInt32OrZero(log_attributes['response.status_code']) as status_code,
     event_message
   from logs
   where source = 'edge_logs'
     and log_attributes['request.path'] like '/rest/v1/%'
     and toInt32OrZero(log_attributes['response.status_code']) >= 400
   order by timestamp desc
   limit 100;
   ```

3. Match the status code and message to the failing layer:
   - A PostgREST error code such as `PGRST116` identifies a Database API request or schema-cache problem. Use the [PostgREST error reference](https://postgrest.org/en/v12/references/errors.html).
   - A Postgres SQLSTATE such as `42501`, `42P01`, or `23505` identifies a database error. Use the [Postgres error-code reference](https://www.postgresql.org/docs/current/errcodes-appendix.html).
   - A Cloudflare `5xx` response without a Postgres error can indicate an edge-network or upstream availability problem.
4. If the API log points to Postgres, query Postgres errors over the same time range:

   ```sql
   select
     timestamp,
     log_attributes['parsed.error_severity'] as error_severity,
     log_attributes['parsed.sql_state_code'] as sql_state_code,
     log_attributes['parsed.user_name'] as user_name,
     event_message
   from logs
   where source = 'postgres_logs'
     and log_attributes['parsed.error_severity'] in ('ERROR', 'FATAL', 'PANIC')
     and log_attributes['parsed.user_name'] = 'authenticator'
   order by timestamp desc
   limit 100;
   ```

The Logs Explorer uses ClickHouse. Structured fields are strings in the `log_attributes` map; do not use the deprecated BigQuery `cross join unnest(metadata)` syntax. See [Advanced log filtering](/docs/guides/monitoring-and-debugging/advanced-log-filtering) for field discovery and query syntax.

## Resolve

Apply the resolution for the confirmed layer:

- Correct the client request when its path, filter, body, or authentication is invalid.
- Correct the Data API configuration when PostgREST cannot resolve the schema or object.
- Correct the database permission, Row Level Security policy, schema, constraint, or query named by the SQLSTATE.
- Check [Supabase Status](https://status.supabase.com/) and the relevant Cloudflare error guidance when the edge returned a `5xx` response without a matching database error.

Change one layer at a time. Do not loosen database privileges or Row Level Security only to test whether an error disappears.

## Verify

1. Repeat the same request with the same authenticated role.
2. Confirm that the request returns the expected status and result.
3. Query the same API and Postgres log window and confirm that the original error no longer appears for the new request.
4. Confirm that requests without the required access are still rejected.

## Escalate

Open a [support ticket](/dashboard/support/new) when a repeatable `5xx` response has no corresponding client, PostgREST, or Postgres cause.

Include the project reference, timestamp with time zone, request ID, method, redacted path, status code, and relevant redacted log lines. Do not include access tokens, API keys, or personal information.
