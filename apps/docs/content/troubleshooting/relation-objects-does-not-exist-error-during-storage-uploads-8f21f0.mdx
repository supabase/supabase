## Symptoms

An authenticated Storage upload returns HTTP `500`, and the Postgres logs contain SQLSTATE `42P01` with `relation "objects" does not exist`.

## Confirm the cause

1. Confirm that the service-managed table exists:

   ```sql
   select to_regclass('storage.objects');
   ```

2. Inspect custom policies on `storage.objects` for an unqualified `objects` reference:

   ```sql
   select policyname, qual, with_check
   from pg_policies
   where schemaname = 'storage' and tablename = 'objects';
   ```

3. Inspect project-owned functions called by those policies. A function with a restricted `search_path` must qualify the table as `storage.objects`.
4. Correlate the failing upload in [Storage logs](/dashboard/project/_/logs/storage-logs) and [Postgres logs](/dashboard/project/_/logs/postgres-logs).

## Resolve

- Replace unqualified references such as `objects` with `storage.objects` in the project-owned policy or function identified by the logs.
- Do not add the `storage` schema to the global `authenticated` role search path to mask the reference. Schema qualification makes the dependency explicit and avoids changing name resolution for every authenticated request.
- If `to_regclass('storage.objects')` returns `NULL`, do not recreate the service-managed table manually. Restore the Storage schema from a known-good backup or contact Support.

## Verify

Repeat an upload with the same user, bucket, and object path. Confirm that it succeeds and that neither Storage nor Postgres logs contain a new `42P01` error. Also test an unauthorized path to confirm that its RLS policy still rejects the upload.

## Escalate

Open a [support ticket](/dashboard/support/new) if `storage.objects` is missing, a service-owned policy or function contains the unqualified reference, or the error continues after every project-owned reference is schema-qualified. Include the project reference, timestamp, object path with sensitive segments redacted, and relevant Storage and Postgres log messages.
