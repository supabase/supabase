You can migrate Auth users and their password hashes as part of a supported project backup and restore. Users do not need to recreate their passwords after the rows are restored successfully.

## Session and signing-key continuity

Auth access tokens are signed by the source project's active signing key. The target project does not automatically trust that key:

- If the target project uses a different signing key, existing access tokens from the source project are rejected and users must sign in again.
- Preserving live sessions requires an explicit signing-key migration plan. Asymmetric private keys managed by Supabase cannot be extracted from a project.

Plan this separately from copying Auth rows. Review [JWT signing keys](/docs/guides/auth/signing-keys) before deciding whether session continuity is required. Do not copy or rotate a legacy JWT secret only to avoid asking users to sign in again; that operation also affects legacy `anon` and `service_role` keys and every component that verifies the old secret.

## How to migrate Auth data

There is no one-size-fits-all script for migrating only the Auth schema. Use the supported [backup and restore guide](/docs/guides/platform/migrating-within-supabase/backup-restore), which covers a full project migration and the handling required for service-managed schemas.

After the restore, verify representative password and OAuth sign-ins, identity links, user metadata, triggers that depend on `auth.users`, and the expected RLS behavior. Treat existing sessions as invalid unless you deliberately migrated a compatible signing key.
