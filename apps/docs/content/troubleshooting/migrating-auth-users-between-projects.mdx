You can migrate all tables in the auth schema—including users and their hashed passwords—from one Supabase project to another. This means users do not need to reset or recreate their passwords after migration.

## How to migrate Auth data

Supabase doesn't provide a one-size-fits-all script for migrating only the auth schema, but the process is covered in the [general migration guide](/docs/guides/platform/migrating-within-supabase). You can use either:

- A full `.backup` file from the Supabase Dashboard, or
- SQL export and import with the Supabase CLI (for example, `pg_dump` and `psql`)

## Important: JWT secret and token validity

Each project is provisioned with a unique JWT secret used to sign and verify auth tokens. This has two key implications:

- If the JWT secret is different in the new project, existing tokens become invalid, and users must sign in again to get new tokens.
- If you reuse the original JWT secret in the new project, existing tokens remain valid and users don't need to sign in again.

If your source project uses [JWT signing keys](/docs/guides/auth/signing-keys):

- You can't export the current key.
- If the key is asymmetric (that is, not a shared secret), you can't reuse it in the new project.
- If the key is a shared secret and you have a copy, import it in [JWT Keys](/dashboard/project/_/settings/jwt), then rotate keys to make it the current key.
