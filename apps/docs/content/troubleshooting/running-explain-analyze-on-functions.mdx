Use this article when a database function is slow but its top-level query plan does not show the statements inside the function.

## Symptoms

Running [`EXPLAIN ANALYZE`](https://www.postgresql.org/docs/current/sql-explain.html) on the function call shows a [function scan](https://pganalyze.com/docs/explain/scan-nodes/function-scan) or result node without the nested query plans.

## Confirm the cause

[`auto_explain`](https://www.postgresql.org/docs/current/auto-explain.html) is a pre-installed module that is able to log query plans for queries within functions.

`auto_explain` has a few settings that you still need to configure:

- `auto_explain.log_nested_statements`: log the plans of queries within functions
- `auto_explain.log_analyze`: capture the `explain analyze` results instead of `explain`
- `auto_explain.log_min_duration`: if a query is expected to run for longer than the setting's threshold, log the plan

Changing these settings at a broad scale can lead to excessive logging. Instead, change the configuration within a `begin` and `rollback` block with `set local`. This isolates the settings to the transaction.

<Admonition type="danger">

`auto_explain.log_analyze` runs the function. A rollback does not reverse sequence increments, outbound network requests, or other effects outside the database transaction. Use a safe input and test environment when the function has side effects.

</Admonition>

## Collect the nested plans

```sql
begin;

set local auto_explain.log_min_duration = '0';       -- log all query plans
set local auto_explain.log_analyze = true;           -- use explain analyze
set local auto_explain.log_buffers  = true;          -- use explain (buffers)
set local auto_explain.log_nested_statements = true; -- log query plans in functions

select example_func(); ---<--ADD YOUR FUNCTION HERE

rollback;
```

If needed, you can change these settings for specific roles, but we don't recommend configuring the value below `1s` for extended periods, as it may degrade performance.

For example, you could change the value for the `postgres` role. Reset the setting after the investigation.

```sql
alter role postgres set auto_explain.log_min_duration = '.5s';
```

After running your test, you should be able to find the plan in the [Postgres logs](/dashboard/project/_/logs/postgres-logs?s=duration:). The auto_explain module always starts logs with the term "duration:", which can be used as a filter keyword.

You can also filter for the function in the [Logs Explorer](/dashboard/project/_/logs/explorer):

```sql
select
  timestamp,
  event_message as query_and_plan,
  log_attributes['parsed.user_name'] as user_name
from logs
where source = 'postgres_logs'
  and event_message ilike '%duration:%'
  and event_message ilike '%FUNCTION_NAME%'
order by timestamp desc
limit 100;
```

## Verify

1. Confirm that the log contains a nested plan for the intended function call.
2. Identify the node with the highest actual time, row-count mismatch, or buffer use.
3. Reset any role-level setting after collecting the required plans:

   ```sql
   alter role postgres reset auto_explain.log_min_duration;
   ```

4. Apply one query change at a time and repeat the same test with a safe input.

## Escalate

Open a [support ticket](/dashboard/support/new) if `auto_explain` is unavailable or does not emit nested plans with the documented settings. Include the project reference, Postgres version, function name, redacted settings, timestamp with time zone, and relevant redacted logs.
