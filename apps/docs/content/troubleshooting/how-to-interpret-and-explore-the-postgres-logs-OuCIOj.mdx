Use this article to isolate a Postgres error or activity pattern in the Logs Explorer.

## Symptoms

Use Postgres logs when a database operation fails, a connection is rejected, a background job fails, or an API error includes a Postgres SQLSTATE. Start with the exact timestamp, role, SQLSTATE, or message from the failing operation.

## Confirm the cause

1. Open the [Logs Explorer](/dashboard/project/_/logs/explorer) and select the smallest time range that contains the event.
2. Query recent Postgres errors:

   ```sql
   select
     timestamp,
     log_attributes['parsed.error_severity'] as error_severity,
     log_attributes['parsed.sql_state_code'] as sql_state_code,
     log_attributes['parsed.user_name'] as user_name,
     event_message
   from logs
   where source = 'postgres_logs'
     and log_attributes['parsed.error_severity'] in ('ERROR', 'FATAL', 'PANIC')
   order by timestamp desc
   limit 100;
   ```

3. Narrow the results by a known SQLSTATE, role, or message fragment. For example:

   ```sql
   select timestamp, event_message
   from logs
   where source = 'postgres_logs'
     and log_attributes['parsed.sql_state_code'] = '42501'
     and log_attributes['parsed.user_name'] = 'authenticator'
     and event_message ilike '%permission denied%'
   order by timestamp desc
   limit 100;
   ```

4. If you do not know which structured keys are present, discover them from recent Postgres rows:

   ```sql
   select arrayJoin(mapKeys(log_attributes)) as key, count() as occurrences
   from logs
   where source = 'postgres_logs'
   group by key
   order by occurrences desc
   limit 100;
   ```

The Logs Explorer uses ClickHouse. Structured values are strings in the `log_attributes` map; do not use the deprecated BigQuery `cross join unnest(metadata)` syntax. See [Advanced log filtering](/docs/guides/monitoring-and-debugging/advanced-log-filtering) for query syntax.

## Resolve

Use the SQLSTATE and message to choose the resolution:

- Correct permissions or Row Level Security for `42501`.
- Correct the schema, search path, or relation name for `42P01`.
- Correct the conflicting value or sequence for `23505`.
- Correct credentials, SSL configuration, or connection limits for connection failures.
- Correct the job, function, trigger, or query named by the error.

Use the [Postgres error-code reference](https://www.postgresql.org/docs/current/errcodes-appendix.html) when the SQLSTATE is unfamiliar. To change what Postgres logs, follow [Logging Postgres queries](/docs/guides/monitoring-and-debugging/advanced-log-filtering#logging-postgres-queries) and keep the scope narrow to avoid unnecessary IO and log usage.

## Verify

1. Repeat the operation that produced the error.
2. Confirm that the operation succeeds or returns the expected rejection.
3. Query the same source and confirm that the new request does not produce the original SQLSTATE and message.
4. Confirm that unrelated database operations still succeed.

## Escalate

Open a [support ticket](/dashboard/support/new) when a repeatable database failure has no application, role, schema, resource, or configuration cause in the available evidence.

Include the project reference, timestamp with time zone, SQLSTATE, database role, operation type, relevant redacted log lines, and changes attempted. Do not include credentials, access tokens, query parameters, or row data.
