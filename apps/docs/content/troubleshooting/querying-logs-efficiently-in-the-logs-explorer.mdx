> A complimentary guide exists for the [Postgres logs](/docs/guides/troubleshooting/how-to-interpret-and-explore-the-postgres-logs-OuCIOj) and the [API logs](/docs/guides/troubleshooting/discovering-and-interpreting-api-errors-in-the-logs-7xREI9). This guide covers the querying discipline that applies across every log source.

The [Logs Explorer](/dashboard/project/_/logs/explorer) lets you write SQL against your project's logs. On paid plans, [these queries are billed by the amount of data scanned](/docs/guides/platform/manage-your-usage/logs-query), so a broad, unfiltered query is not just slow: it costs more, and it buries the one line you need under everything you don't. This guide covers the discipline for writing narrow, fast queries, and the syntax quirks specific to the Logs Explorer's SQL dialect.

## Query narrow, widen deliberately

Efficient debugging usually takes a handful of queries, not one big one:

1. **Query one `source` at a time.** All logs live in a single `logs` table, tagged by a `source` column (`edge_logs`, `postgres_logs`, `auth_logs`, and so on). Pick the source for the service you suspect first, and always filter on it: `select ... from logs where source = 'edge_logs'`.
2. **Filter on `timestamp` first.** Add a bounded time range before anything else. An unfiltered query over your full retention window is the single most common cause of a slow or expensive run.
3. **Select only the columns you need.** Never pull back the whole `log_attributes` map; read the specific keys you're filtering or displaying with bracket access, for example `log_attributes['response.status_code']`.
4. **Widen along an anchor, not from scratch.** Once a query gives you a `timestamp`, a request path, or a `sql_state_code`, use it to query the next source. For a failing API request, take its `timestamp` from `edge_logs` and look at `postgres_logs` around that same window for the underlying database error.

The anti-pattern this discipline exists to avoid: an unfiltered scan (the Logs Explorer already blocks `select *`, but the equivalent is reading every key out of `log_attributes`) with no time bound, across a multi-day window. It's slow, it scans more data than needed, and the extra rows make the actual cause harder to spot.

## Know the SQL dialect

The Logs Explorer runs ClickHouse SQL against the `logs` table (the `logs.all.otel` analytics endpoint), with a few restrictions to keep queries fast:

- No `select *` or `count(*)`. List the columns you need, and use `count()`.
- `log_attributes` is a `Map(String, String)`. Read a field with bracket access, for example `log_attributes['request.method']`; there's no unnesting join. Map values are strings, so wrap numeric fields in `toInt32OrZero(...)` before comparing or aggregating.
- Use `ilike` for case-insensitive substring matching, and `match(column, 'pattern')` for regex.
- `timestamp` is a native `DateTime64` column. Filter, order, and compare it directly, no cast needed.
- Discover the keys a source actually sets with `arrayJoin(mapKeys(log_attributes))` rather than guessing.

## Essential diagnostic queries

Failing API requests by status code:

```sql
-- failing api requests, last 15 minutes
select
  timestamp,
  log_attributes['request.method'] as method,
  log_attributes['request.path'] as path,
  log_attributes['response.status_code'] as status
from logs
where source = 'edge_logs'
  and toInt32OrZero(log_attributes['response.status_code']) >= 400
  and timestamp > now() - interval 15 minute
order by timestamp desc
limit 100;
```

A specific SQLSTATE (for example `42501` permission denied, `42P01` relation missing, `23505` duplicate key):

```sql
-- permission denied errors, last 15 minutes
select
  timestamp,
  log_attributes['parsed.user_name'] as user_name,
  log_attributes['parsed.error_severity'] as severity,
  event_message
from logs
where source = 'postgres_logs'
  and log_attributes['parsed.sql_state_code'] = '42501'
  and timestamp > now() - interval 15 minute
order by timestamp desc
limit 100;
```

Free-text search across raw messages, using `ilike` for a case-insensitive match:

```sql
-- deadlocks, last hour
select timestamp, event_message
from logs
where source = 'postgres_logs'
  and event_message ilike '%deadlock%'
  and timestamp > now() - interval 1 hour
order by timestamp desc
limit 100;
```

## Widen along an anchor to follow a request across services

Once one query surfaces a timestamp, take that same window into the next source rather than starting over with a broad scan. For example, a `5xx` from `edge_logs` might originate in Postgres:

```sql
-- postgres errors around a known edge_logs timestamp
select
  timestamp,
  log_attributes['parsed.error_severity'] as severity,
  log_attributes['parsed.sql_state_code'] as sql_state,
  event_message
from logs
where source = 'postgres_logs'
  and timestamp between '2026-05-06T04:44:00' and '2026-05-06T04:46:00'
  and log_attributes['parsed.error_severity'] in ('ERROR', 'FATAL', 'PANIC')
order by timestamp desc
limit 100;
```

Narrowing the window to a couple of minutes around the anchor timestamp keeps the query fast and puts the relevant rows at the top, instead of scanning hours of unrelated traffic.

## Other ways to read logs

For "what just failed" during active debugging, the [Supabase MCP server's `get_logs` tool](/docs/guides/ai-tools/mcp) returns the last 24 hours for a given service without writing SQL. For recurring export or monitoring instead of one-off debugging, configure a [log drain](/docs/guides/telemetry/log-drains) to stream logs to an external sink rather than polling the Logs Explorer on a schedule.
