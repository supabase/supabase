Use this article to find the operation that prevents an Edge Function from responding before the request idle timeout and reduce or move that work.

## Symptoms

An Edge Function request returns HTTP `504 Gateway Timeout`. Supabase did not receive the start of a response before the [150-second request idle timeout](/docs/guides/functions/limits#runtime-limits).

A `504` identifies a response timeout. Other runtime limits can produce different status codes or shutdown reasons. Check [Edge Function status codes](/docs/guides/functions/status-codes) when the response is not `504`.

## Confirm the cause

1. Reproduce the request and record its timestamp with time zone, function path, representative input, and execution ID when one is available.
2. Open the [Logs Explorer](/dashboard/project/_/logs/explorer) and find recent `504` responses:

```sql
select
  timestamp,
  log_attributes['request.pathname'] as function_path,
  toInt32OrZero(log_attributes['response.status_code']) as status_code,
  toFloat64OrZero(log_attributes['execution_time_ms']) as execution_time_ms
from logs
where source = 'function_edge_logs'
  and toInt32OrZero(log_attributes['response.status_code']) = 504
order by timestamp desc
limit 20;
```

3. Compare the execution time for the affected function path:

```sql
select
  log_attributes['request.pathname'] as function_path,
  toInt32OrZero(log_attributes['response.status_code']) as status_code,
  avg(toFloat64OrZero(log_attributes['execution_time_ms'])) as avg_runtime_ms,
  min(toFloat64OrZero(log_attributes['execution_time_ms'])) as min_runtime_ms,
  max(toFloat64OrZero(log_attributes['execution_time_ms'])) as max_runtime_ms
from logs
where source = 'function_edge_logs'
  and log_attributes['request.pathname'] = '/functions/v1/YOUR_FUNCTION_NAME'
group by function_path, status_code
limit 20;
```

4. Add `console.time` around suspected operations, deploy the instrumentation, and reproduce the request:

```js
console.time('fetch-user-data')
const userData = await fetchUserFromDatabase(id)
console.timeEnd('fetch-user-data')
```

5. Find the timing labels in the function logs and identify the operation that consumes the response window. You can also step through the function locally with [developer tools](/docs/guides/functions/debugging-tools).

Common causes include:

- Independent API calls that run sequentially
- Slow or unindexed database queries
- External APIs that throttle requests or respond slowly
- Loops or blocking operations that do not complete
- Request payloads that cause substantially more work

The cause is confirmed when the function and request logs show that a specific operation prevents the function from starting a response before the timeout.

## Resolve

Choose the smallest change that addresses the confirmed slow operation.

### Run independent requests concurrently

When two requests do not depend on each other, start them together:

```js
// Before: total time is the duration of A plus B.
const resultA = await fetch('https://api-one.com/data')
const resultB = await fetch('https://api-two.com/data')

// After: total time is the longer duration of A or B.
const [resultA, resultB] = await Promise.all([
  fetch('https://api-one.com/data'),
  fetch('https://api-two.com/data'),
])
```

Do not run requests concurrently when one operation depends on the result of another or when concurrency would exceed a downstream service's limits.

### Reduce work in the request

Split unrelated operations into separate functions or move work that does not affect the response into a [background task](/docs/guides/functions/background-tasks). Background tasks remain subject to Edge Function runtime limits.

If the function waits for an external API, configure a timeout and a fallback or error response so that the request does not wait until the platform limit.

### Optimize database operations

Inspect database calls in [Query Performance](/dashboard/project/_/advisors/query-performance). Use the [Performance Advisor](/dashboard/project/_/advisors/performance) and [index guide](/docs/guides/database/postgres/indexes#index-advisor) when the evidence identifies a slow query or missing index.

### Cache repeated reads

When the function repeatedly reads data that changes infrequently, use a cache with an expiration and invalidation policy. See the [Upstash Redis example](/docs/guides/functions/examples/upstash-redis).

### Limit request size

If processing time changes with request size, inspect the content length recorded in request headers:

```sql
select
  log_attributes['request.pathname'] as function_name,
  toInt32OrZero(log_attributes['response.status_code']) as status_code,
  avg(toInt32OrZero(log_attributes['request.headers.content_length'])) as avg_content_size_in_bytes,
  min(toInt32OrZero(log_attributes['request.headers.content_length'])) as min_content_size_in_bytes,
  max(toInt32OrZero(log_attributes['request.headers.content_length'])) as max_content_size_in_bytes
from logs
where source = 'function_edge_logs'
  and log_attributes['request.pathname'] = '/functions/v1/YOUR_FUNCTION_NAME'
group by function_name, status_code
limit 10;
```

Validate the payload and reject inputs that exceed the size or complexity your function is designed to process.

### Move work that cannot fit the runtime

The request idle timeout cannot be increased. If the operation cannot start a response within the limit after optimization, move the long-running work to a service designed for that duration, redesign the operation as a job that the client can poll, or [self-host Edge Functions](/docs/reference/self-hosting-functions/introduction) with runtime limits appropriate for your environment.

## Verify

1. Deploy the change to the same environment that produced the timeout.
2. Repeat the request with representative input, including the input size that previously failed.
3. Confirm that the request starts a response before 150 seconds and returns the expected status and body.
4. Inspect the Edge Function request and function logs over the new time window. Confirm that the new request has no `504` and that the identified operation completes within its expected duration.
5. Repeat the request enough times to distinguish a consistent improvement from one faster response.

## Escalate

Open a [support ticket](/dashboard/support/new) if requests still return `504` after the function starts a response within the documented timeout, or if the logs do not contain the request or execution evidence needed to identify the slow operation.

Include the project reference, function name, deployment version, timestamps with time zone, execution IDs, sanitized request shape, relevant timing output, changes attempted, and verification results. Do not include API keys, access tokens, or request data that has not been redacted.

For application-level debugging, also review [Edge Function debugging tools](/docs/guides/functions/debugging-tools) and [error handling](/docs/guides/functions/error-handling).
