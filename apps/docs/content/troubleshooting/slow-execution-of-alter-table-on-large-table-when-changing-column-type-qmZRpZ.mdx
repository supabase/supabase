Use this article when changing a column type on a large table runs for too long or blocks other queries.

## Symptoms

- `alter table ... alter column ... type` remains active for longer than expected.
- Reads or writes wait on the table while the change runs.
- The statement reaches its timeout before the rewrite completes.

## Confirm the cause

1. Check active and blocked queries with [`supabase inspect db long-running-queries`](/docs/reference/cli/usage#supabase-inspect-db-long-running-queries), `blocking`, and `locks`.
2. Confirm that the `alter table` statement is active or waiting and identify the session that blocks it.
3. Check the table size and determine whether the conversion requires rewriting existing rows. Many type changes rewrite the whole table; a metadata-only conversion finishes much sooner.
4. Review database CPU, memory, and disk IO over the same time window. Resource pressure can extend a rewrite, but increasing compute does not remove its lock requirements.

## Resolve

For a maintenance window where blocking writes is acceptable, run the direct type change from an external Postgres client with a session timeout that covers the tested duration.

For a table that must keep serving writes, use an expand-and-contract migration:

1. Add a nullable column with the new type:

   ```sql
   alter table public.table_name add column new_column_name new_data_type;
   ```

2. Update the application or add reviewed database logic to write both the old and new columns during the migration.
3. Backfill the new column in bounded batches using a stable primary-key range. The assignment direction is from the old column to the new column:

   ```sql
   update public.table_name
   set new_column_name = old_column_name::new_data_type
   where id > :batch_start
     and id <= :batch_end
     and new_column_name is null;
   ```

4. Validate the converted values and update reads to use the new column.
5. Remove the old column and rename the new column in a later maintenance window after dependent views, functions, policies, indexes, and application code have been updated.

Do not run a single unbounded `update` and assume that it avoids a prolonged transaction. Test the cast and batch size on a representative environment, and keep a recoverable backup before the migration.

## Verify

1. Compare non-null row counts and application-level invariants between the old and new columns.
2. Confirm that the application reads and writes the new type correctly.
3. Check for blocked queries, conversion errors, and increased resource pressure after each batch.
4. Confirm that no database object or application code still depends on the old column before dropping it.

## Escalate

Open a [support ticket](/dashboard/support/new) if the type change remains blocked and the blocking session cannot be identified, or if the database becomes unavailable during the migration.

Include the project reference, table size, source and destination types, timestamps with time zone, relevant redacted lock information, batch size, and steps attempted.
