Use this article to identify the cause of sustained database CPU usage and decide whether to optimize the database or change its compute size.

## Symptoms

High CPU usage can cause:

- Queries to respond more slowly
- Daily backup operations to be disrupted
- The database to become unresponsive in rare cases
- Less capacity to absorb a traffic increase

Each Supabase project runs on dedicated compute. The available resources depend on the project's [compute size](/docs/guides/platform/compute-and-disk).

## Confirm the cause

1. Open the [Database Health report](/dashboard/project/_/observability/database), select the affected project, and identify when CPU usage increased.
2. If you collect the project's [Metrics API](/docs/guides/monitoring-and-debugging/metrics), inspect CPU over the same time window. Confirm whether the increase is sustained or limited to a known operation.
3. Open [Query Performance](/dashboard/project/_/advisors/query-performance?preset=slowest_execution). Look for queries whose execution time or call volume increased during the affected window.
4. Use [database inspection tools](/docs/guides/database/inspect#query-performance) to check for long-running queries, outliers, sequential scans, and inefficient index usage when you need more detail.
5. Review the [Performance Advisor](/dashboard/project/_/advisors/performance) for missing indexes and other database findings related to the affected queries.
6. Compare the evidence with these common causes:
   - **Slow or frequent queries:** Query execution time or call volume increased with CPU usage.
   - **Missing indexes:** The Performance Advisor or a query plan shows that a query scans more rows than needed.
   - **Insufficient compute:** CPU remains elevated after avoidable query and indexing problems have been ruled out, or the increase corresponds to expected traffic and operations.

Do not upgrade compute only because one short spike appears in a report. Confirm that the resource demand is sustained or repeats with the affected operation.

## Resolve

Apply the resolution that matches the confirmed cause:

- For slow or frequent queries, use the [query optimization guide](/docs/guides/database/query-optimization) to reduce execution cost or call volume.
- For a missing index, review the query and create the specific index recommended by your query analysis. Use the [index guide](/docs/guides/database/postgres/indexes) to evaluate the index before adding it to production.
- For expected demand that exceeds the available resources, change the project's [compute size](/dashboard/project/_/settings/infrastructure).

Apply one change at a time so that you can measure its effect. Record the previous query, index, or compute configuration before you change it.

## Verify

1. Repeat the operation or representative traffic that produced the CPU increase.
2. Compare CPU usage over an equivalent time window in the Database Health report or your metrics system.
3. Confirm that affected query latency and call volume meet your expected range in Query Performance.
4. Check the Performance Advisor again when the resolution addressed a database finding.
5. Confirm that normal application requests and scheduled operations still succeed.

The issue is resolved when the original operation succeeds and CPU usage returns to the range that your database can sustain.

## Escalate

Open a [support ticket](/dashboard/support/new) if CPU remains elevated after you have ruled out slow queries, excessive query volume, and missing indexes, or if the database remains unresponsive after a compute change.

Include the project reference, timestamps with time zone, screenshots or exported values from the affected window, relevant query identifiers, advisor findings, changes attempted, and verification results. Do not include database credentials or data that has not been redacted.
