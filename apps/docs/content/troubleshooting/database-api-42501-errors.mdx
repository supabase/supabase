Use this article to identify which Postgres permission rejected a Database API request and grant only the access that the operation requires.

## Symptoms

The Database API returns an HTTP `401` or `403` response with Postgres error code `42501`. The message might identify a schema, table, column, or row-level security policy that rejected the operation.

## Confirm the cause

1. Reproduce the request and record its timestamp with time zone, HTTP status, operation, table or function, and database role.
2. Inspect the API logs for the request. Confirm that the response contains SQLSTATE `42501`, and record its request ID when one is available.
3. Open the [Logs Explorer](/dashboard/project/_/logs/explorer) and run this query over the same time window:

```sql
select
  timestamp,
  event_message,
  log_attributes['parsed.error_severity'] as error_severity,
  log_attributes['parsed.user_name'] as user_name,
  log_attributes['parsed.sql_state_code'] as sql_state_code
from logs
where source = 'postgres_logs'
  and log_attributes['parsed.sql_state_code'] = '42501'
order by timestamp desc
limit 100;
```

4. Use `user_name` and `event_message` to identify the rejected role, resource, and operation.
5. Match the evidence to one cause:
   - **Restricted schema:** The request tried to access a protected schema such as `auth` or `vault`.
   - **Custom schema permission:** The request used a custom schema that is not configured for Database API access or lacks the required grants.
   - **Table privilege:** The message contains `permission denied for table`, and the role lacks the privilege required by the operation.
   - **Column privilege:** The request reads or writes a restricted column. A `select *` request also selects restricted columns.
   - **Row-level security policy:** An `INSERT` or `UPDATE` request reaches the table but does not satisfy a policy for the request role.

The error is not confirmed as an RLS issue only because the table has RLS enabled. Use the Postgres log detail and the role's grants and policies to distinguish the cause.

## Resolve

Apply the resolution for the confirmed cause.

### Restricted schema

Do not grant `anon` or `authenticated` direct access to protected schemas such as `auth` or `vault`. If your application needs a specific operation, expose only that operation through a carefully reviewed database function. See [security definer and invoker functions](/docs/guides/database/functions?queryGroups=language&language=sql&queryGroups=example-view&example-view=sql#security-definer-vs-invoker).

### Custom schema permission

Follow [Using custom schemas](/docs/guides/api/using-custom-schemas) to expose the intended schema and grant the required permissions. Do not expose schemas or tables that the application does not need.

### Table privilege

Check the current privileges for the affected table and role:

```sql
select grantee, privilege_type
from information_schema.role_table_grants
where table_schema = 'public' and table_name = 'your_table';
```

Grant only the privilege required by the operation. For example, this statement grants read access:

```sql
grant select on table public.your_table to authenticated;
```

You can also configure Data API table access from [**Project Settings > Data API**](/dashboard/project/_/integrations/data_api/settings).

<Admonition type="danger">

Granting a role access to a table can expose that table through the Data API. Enable row-level security on every table in an exposed schema, and create policies that restrict rows to the intended users. See [Securing your API](/docs/guides/api/securing-your-api).

</Admonition>

### Column privilege

Select only the columns that the role can read, or update the column privileges when the application requires the restricted column. Review the effective role before broadening column access.

### Row-level security policy

Create or correct a policy for the affected operation and role. An `UPDATE` also needs a matching `SELECT` policy. Use both `USING` and `WITH CHECK` when an update must restrict the existing row and its new values. See [Row Level Security](/docs/guides/database/postgres/row-level-security).

## Verify

1. Repeat the exact API request with the same key, session, database role, operation, and representative data.
2. Confirm that the response succeeds and returns or changes only the intended data.
3. Query API and Postgres logs over the new time window. Confirm that the repeated request no longer produces SQLSTATE `42501`.
4. Repeat a negative test with a role or row that must remain unauthorized. Confirm that the request is still rejected or returns no protected data.

The issue is resolved only when the intended request succeeds and unauthorized access remains blocked.

## Escalate

Open a [support ticket](/dashboard/support/new) if the Postgres logs show the expected role and permissions but the request continues to return `42501`, or if you cannot identify the rejected permission from the log detail.

Include the project reference, timestamp with time zone, request ID, sanitized API response, Postgres log detail, affected role and operation, relevant grants and policies, changes attempted, and verification results. Do not include API keys, JWTs, passwords, or table data that has not been redacted.
