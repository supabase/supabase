## Symptoms

A Storage upload returns HTTP `403` with `new row violates row-level security policy`.

## Confirm the cause

1. Confirm that the request includes a valid user session and record the user's ID, bucket, object path, and whether the upload uses `upsert`.
2. Inspect the [Storage logs](/dashboard/project/_/logs/storage-logs) and [Postgres logs](/dashboard/project/_/logs/postgres-logs) for the same request.
3. Review the policies on `storage.objects` in the [policy editor](/dashboard/project/_/auth/policies) or query `pg_policies`.
4. Match the request to the required operation:
   - A new upload requires an `INSERT` policy whose `WITH CHECK` expression accepts the bucket, path, and user.
   - Overwriting with `upsert` additionally requires `SELECT` and `UPDATE` policies.

## Resolve

Create or correct only the policies required by the intended operation. Follow [Storage access control](/docs/guides/storage/security/access-control) and use Storage helper functions to constrain bucket and folder access. Do not add a broad `SELECT` policy to fix a new upload that does not use `upsert`; first correct the rejected `INSERT` expression or the request's session, bucket, and path.

## Verify

Repeat the upload with the same authenticated user and path. Confirm that it succeeds, then test another user or path that should remain unauthorized. For `upsert`, verify both creating a new object and overwriting an existing object.

## Escalate

Open a [support ticket](/dashboard/support/new) if the logs show the expected role and policy inputs but Postgres evaluates a different identity, bucket, or path. Include the project reference, timestamp, operation, sanitized policy definitions, and redacted object path. Do not include JWTs or Storage credentials.
